# ADR-0041: Gemini 503만 지수 backoff로 두 번 더 호출해요

- 상태: 확정
- 작성·확정일: 2026-11-22
- 확정 근거: 2026-11-22 사용자가 #17 검증 중 운영 모델을 3.6으로 복원하고 지수 backoff 추가를 요청했어요.
- 관련 기록: [ADR-0032](0032-gemini-single-call.md)를 대체해요. [ADR-0018](0018-api-contract-and-policies.md)의 사용자 재시도·할당량 정책과 [ADR-0024](0024-direct-summary-http.md)의 하루 3회 접수는 유지해요. [ADR-0040](0040-pending-channel-summary-policy.md)의 대기 정책과는 별개예요.
- 구현·검증 상태: 코드와 workerd 회귀 검사를 구현하고 로컬 검사를 통과했어요. 배포와 실제 503 재시도 관찰은 #17에서 확인해요.

## 문제와 현재 상태

[ADR-0032](0032-gemini-single-call.md)는 무료 한도와 결과 불명을 줄이려고 `interactions.create`에 `retries: { strategy: "none" }`을 넘겼어요.
그래서 `gemini-3.6-flash`의 `503 service_unavailable`이 한 번 나면 사용자가 직접 재시도해야 했어요.
11월 3일과 10일 기록에도 같은 모델의 503이 남아 있어요([Gemini 기록](../gemini.md)).

2026-11-22 라이브 배포는 `GEMINI_MODEL=gemini-3.8-flash`로 실행됐지만 코드의 허용 목록에는 3.8이 없어
새 요약이 `503 SUMMARY_UNAVAILABLE`이 됐어요. 운영 모델을 `gemini-3.6-flash`로 복원하고 최신 main `558bedd`를 배포했어요.
이 결정은 그 배포 뒤에도 3.6의 일시 503을 사용자 개입 없이 줄이는 범위예요.

## 결정

- `interactions.create`에 `attempt-count-backoff`를 넘겨 503만 같은 실행 안에서 최대 두 번 더 호출해요.
  간격은 5초, 10초이고 최대 10초예요. SDK jitter로 최대 25% 짧아질 수 있어요.
- `retry_codes`는 `["503"]`만 둬요. 408·409·429·500·502·504·연결 오류·시간 초과는 재시도하지 않아요.
- 재시도는 기존 600초 중단 신호 안에서만 실행해 실행권 660초를 넘기지 않아요.
- 생성 설정의 `sdkRetries: "default"`는 바꾸지 않아요. 재시도는 전송 정책이고 리포트 내용·생성 키와 무관해요.
- 사용자 재시도 3회와 계정별 하루 3회 접수 정책은 그대로예요. 자동 재시도는 새 접수나 추가 차감을 만들지 않아요.

## 근거와 대안

2026-11-22 저장소에 설치된 `@google/genai` 2.31.0의 타입과 구현을 확인했어요.
`RetryConfig`는 `attempt-count-backoff`와 `maxRetries`를 지원하고, `retry_codes`로 재시도할 상태 코드를 제한할 수 있어요.
SDK 기본값은 408·409·429·5XX에 최대 4번 더 호출하므로 그대로 쓰지 않고 범위를 좁혔어요.

- 503은 서비스가 요청을 처리하지 못했다는 응답이라는 ADR-0032의 판단을 유지해요.
  그래서 같은 요청을 다시 보내도 중복 생성으로 보지 않아요.
- 429는 무료 RPD 20을 실패로 더 쓰게 되어 제외해요. 500·502·504와 연결 오류는 처리 여부가 불명확해 제외해요.
- 실패 1건이 Gemini 호출을 최대 3회 쓸 수 있어요. 하루 20회 한도와 동시 사용자 수를 함께 봐야 해요.
- 작업 큐에서 분 단위로 자동 재시도하는 대안은 사용자 요청 전에는 다시 호출하지 않는다는 ADR-0024의 정책과
  attempt·lease 의미를 바꾸므로 채택하지 않았어요. 503이 몇 분씩 이어지는 것이 확인되면 다시 검토해요.

## 가정·한계와 영향

- 실제 503 지속 시간과 재시도 성공률은 아직 측정하지 않았어요.
- 503 응답이 과금되지 않는다는 보장은 없어요.
- 자동 재시도 횟수는 HTTP 응답에 노출하지 않아요. 최종 실패만 사용자 재시도 1회로 남아요.
- 재시도 지연은 최대 10초이고, 1분 Cron 주기와 별개로 같은 실행 안에서 기다려요.
- 공급자 응답이 늦게 성공하는 경우의 결과 불명 처리는 기존 실행권·lease 규칙을 따라요.

## 검증과 재검토 조건

- workerd에서 503 두 번 뒤 성공 시 요청 3회와 성공 결과, 503 세 번 시 `temporary`·503과 요청 3회, 429 시 요청 1회를 확인해요.
- `mise run api:check`와 `git diff --check`를 통과해야 해요.
- 배포된 Worker에서 실제 503 재시도와 무료 한도 소비는 #17에서 확인하고, 확인 전에는 완료로 보고하지 않아요.

## 반론과 변경 이력

- 2026-11-22: ADR-0032의 단일 호출을 대체하고 503 한정 지수 backoff를 채택했어요.
