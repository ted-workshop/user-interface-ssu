# ADR-0024: 직접 요약 HTTP를 기존 세션·영속 실행기에 연결해요

- 상태: 확정
- 작성·확정일: 2026-10-30
- 확정 근거: 사용자가 #11 구현과 계정별 하루 3회 상한을 승인했어요. 기존 계약 적용과 접수 차감 방식은 승인 범위 안에서 판단했어요.
- 관련 기록: [ADR-0018](0018-api-contract-and-policies.md)의 인증·HTTP 정책, [ADR-0020](0020-shared-analysis-and-report-permissions.md)의 공통 보고서, [ADR-0023](0023-background-runner-readability.md)의 실행기를 적용해요.
- 구현·검증 상태: HTTP·세션 조회·접수 차감·채널 출처 저장을 구현하고 로컬 API·공통 도구·Android·인프라 검사를 통과했어요. 로그인 발급·실제 공급자·원격 배포·Android 연결은 남아 있어요.

## 문제와 현재 상태

원격 main `e76652e`에는 공통 분석 접수·실행·복구 함수가 있지만 HTTP는 `/health`뿐이에요.
[#11](https://github.com/ted-workshop/user-interface-ssu/issues/11)은 URL 접수 후 앱을 닫아도 같은 요청을
다시 조회하고, 실패했을 때 조회 재시도와 분석 재시도를 구분해야 해요. #9의 세션 발급과 #12의
리포트 조회는 다른 담당자의 후속 작업이에요. #5의 현재 생성 설정 검증과 #7의 프로젝트 공유 한도 검토도 남아 있어요.

## 결정

- `POST /v1/summary-requests`, 목록·개별 `GET`, `POST /v1/summary-requests/{id}/retry`를 연결해요.
  입력·cursor·필터는 Zod strict schema로 확인하고 Hono의 body limit으로 본문을 16 KiB까지 받아요.
- `requireSession`은 Bearer 토큰의 SHA-256으로 기존 sessions를 조회하고 절대 만료·이메일 확인을 검사해요.
  삭제된 세션은 401이에요. 사용자 ID를 본문에서 받지 않고 모든 개인 조회에 세션 userId를 bind해요.
  개인 응답은 no-store, 타인 요청과 없는 요청은 같은 404예요. 가입·비밀번호·토큰 발급은 추가하지 않아요.
- 접수·재시도는 기존 작업 함수에 맡겨요. HTTP에서는 공급자를 호출하지 않으며 저장 후 Location과
  요청 객체를 반환해요. 새 대기 요청·실행 재시도는 202, 이미 있는 요청·완성 결과·같은 retry는 200이에요.
  실패한 공통 작업의 재접수도 같은 실패 요청을 반환하고 새 분석을 만들지 않아요.
- 목록은 본인 요청만 시간·ID 내림차순으로 반환해요. 내부 작업 ID·시도 원문·공급자 정보는
  명시적인 응답 변환에서 제외하고 Unix 초는 UTC 문자열로 바꿔요. 조회는 상태를 변경하지 않아요.
- 직접 요약의 새 공통 분석과 명시적 재시도를 계정별 UTC 하루 합계 3회로 제한해요. 사용자가 정한
  값으로 구현하며 별도 상한 환경변수는 추가하지 않아요. 키·모델이 준비되지 않으면 새 분석은 503이에요.
  기존 상태 조회와 식별 가능한 생성 설정의 결과 재사용은 유지해요. Cron의 실행 방식은 ADR-0023 그대로예요.
- `0005_summary_admissions.sql`은 작업·접수할 시도 번호·접수 사용자·시각을 저장해요.
  UTC 당일 상한 검사와 접수·차감을 같은 D1 batch로 처리해 동시 요청의 초과 접수를 막아요.
  새 실행을 시작한 사용자만 차감하고, 다른 사용자의 합류·완성 보고서 재사용·응답 재전달은 차감하지 않아요.
  실패·결과 불명의 접수 기록도 보존하며 기존 작업은 소급 차감하지 않아요.
- 재시도는 관찰한 시도 번호와 기존 3시도 규칙을 유지해요. 중지한 채널·비활성 수신 주소 때문에
  실행할 수 없는 요청도 조회와 실제 상태 전이에서 거부해요. 한도 소진 때는 retryable=false,
  실제 새 retry 요청에는 429와 다음 UTC 자정까지의 Retry-After를 반환해요.
- oEmbed의 author_url이 HTTPS YouTube 채널 주소이면 보고서의 channel_url에 저장해요.
  없거나 잘못된 값이면 null이며 채널명으로 추측하지 않아요. 생성 프롬프트·모델·SDK 재시도는 유지해요.

## 근거와 대안

2026-10-30 설치된 Hono 4.13.12의 body-limit 구현과 [공식 문서](https://hono.dev/docs/middleware/builtin/body-limit)를 확인했어요.
기존 미들웨어가 Content-Length 또는 실제 본문 스트림의 크기를 확인하므로 별도 본문 수집기를 만들지 않아요.
Workers 최신 타입 5.20261030.1과 저장소 고정 타입의 D1 prepare·batch 형태도 확인했어요.

[D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)는 순차 SQL을 하나의
트랜잭션으로 처리해요. [SQLite changes()](https://www.sqlite.org/lang_corefunc.html#changes)는 직전 변경문의
직접 변경 수를 제공해요. 재시도 UPDATE가 실제로 성공했을 때만 바로 다음 INSERT에서 차감하고,
이 순서와 저장 실패 rollback은 workerd·로컬 D1 행동 검사로 확인해요.

HTTP에서 먼저 횟수를 읽고 나중에 접수하면 동시 요청이 같은 잔여량을 소비할 수 있어요.
실행 시도만 세면 아직 실행하지 않은 접수·retry가 누락돼요. 접수 차감 표 하나로 이 둘을 함께 처리해요.
KV·Durable Object를 추가하면 별도 저장소와 D1 사이의 일관성을 다시 해결해야 하므로 도입하지 않아요.

인증을 완료할 때까지 모든 HTTP 구현을 기다리거나 임의 사용자 ID를 허용하는 대안 대신,
이미 확정한 세션 표를 검사해 #9에서 발급할 실제 토큰을 그대로 받을 수 있게 해요.
테스트용 세션 발급·인증 우회 경로는 제품 API에 만들지 않아요.

## 가정·한계와 영향

- 계정별 접수 수는 SDK의 물리 HTTP 요청 수·Google 프로젝트 전체 사용량·과금량이 아니에요.
  하루 3회의 운영 적합성은 #5·#7에서 실제 사용량과 함께 확인해야 해요. 이 값만으로 공급자 성공을 입증하지 않아요.
- 원격 Variable·D1·Worker는 변경하지 않아요.
- 0005는 새 표·인덱스만 추가해요. 기존 세션·작업·시도·보고서의 값을 바꾸지 않아요.
- #9 가입·로그인·메일 복구, #12 보고서 본문 조회·검색, Android UI는 구현 범위 밖이에요.
  이번 HTTP 응답의 reportId 이후 실제 본문 읽기와 로그인은 해당 기능이 연결된 뒤 검증해야 해요.
- 공급자 성공·원본 시간 링크 대조·원격 CPU·Cron 지연을 검사하지 않았어요. #11 전체 완료를 선언하지 않아요.

## 검증과 재검토 조건

새 HTTP 검사 3개가 기존 코드의 404 때문에 실패하는 것을 먼저 확인했어요.
세션 만료·삭제·미확인 이메일, URL 변형·동시 중복 접수, 타인 접근, 페이지 cursor,
본문 상한, 일일 상한 경쟁, 반복 retry·오래된 attempt, 결과 불명, 보고서 공유·직접 메일 없음,
저장 실패 rollback·채널 출처를 실제 workerd·로컬 D1과 공급자 fixture로 검사했어요.

2026-10-31 최종 구현 기준으로 확인한 결과예요.

- 로컬 SDK를 `ANDROID_HOME`으로 지정한 `mise run check`에서 workerd 226개,
  API 도구 16개, 공통 도구 49개로 총 291개 테스트를 통과했어요. 포맷·타입·생성 타입 확인,
  Worker 배포 dry-run과 Android 포맷·lint·단위 테스트·debug 빌드도 통과했어요.
- 같은 전체 검사의 Terraform 단계는 외부 레지스트리 응답 시간 초과로 실패했어요.
  해당 단계만 `mise run infra:check`로 다시 실행해 state·cloudflare 구성의 초기화와 검증을 통과했어요.
  원격 backend·리소스에는 접근하지 않았어요.
- 격리된 로컬 D1에 `mise run api:db:migrate`로 0001부터 0005까지 적용했고,
  재실행 때 추가 적용할 migration이 없었어요. 실제 스키마와 ERD의 18개 표·126개 열이 일치하고,
  ERD의 논리 관계는 29개이며 `foreign_key_check` 위반은 0개였어요.
- 일일 접수 조회가 사용자·시각 인덱스를 사용하고, 목록 cursor가 소유자·시간·ID 복합 인덱스의
  범위 검색을 사용하는 것을 로컬 SQLite 실행 계획으로 확인했어요.
- 변경 문서의 상대 링크와 `git diff --check`, 최종 diff·Git 상태를 확인했어요.
  검사는 `e76652e`에서 만든 `feature/11-summary-api-1030a` worktree의 변경을 기준으로 했어요.
  위 결과에 원격 CI·배포와 실제 Gemini·SMTP·기기 검증은 포함하지 않아요.

구현은 [HTTP 경계](../../apps/api/src/summary-requests.ts), [세션 검사](../../apps/api/src/auth.ts),
[접수·재시도](../../apps/api/src/jobs/analysis.ts), [HTTP 행동 검사](../../apps/api/test/summary-requests.test.ts)에 있어요.

기존 #5 worktree의 공급자 오류 처리·실제 검증 기록은 가져오거나 수정하지 않았어요.
나중에 통합할 때 summary.ts와 api-contract.md의 서로 다른 변경을 함께 보존해야 해요.

운영 상한이 실행 시간·프로젝트 공유량 기준으로 바뀌거나 #9의 세션 계약이 바뀌면 이 경계를 재검토해요.
계정별 공개 보고서 이용 권한과 새 분석 생성 권한을 구분해야 하는 제품 요구가 생겨도 다시 검토해요.

## 반론과 변경 이력

- 2026-10-30: HTTP 연결과 로컬 검증을 먼저 진행하고 실제 인증·공급자·기기 연결은 별도로 남겼어요.
  사용자가 하루 3회를 선택해 새 분석·명시적 재시도의 합계 상한으로 적용했어요.
- 2026-10-30: 한도 소진 후에도 retryable=true였던 행동 검사를 추가하고 조회 결과도 현재 잔여량에 맞췄어요.
  중지한 채널의 실패 요청이 공통 작업을 다시 대기시킬 수 있던 경계는 실행 가능 조건을 함께 검사하도록 수정했어요.
- 2026-10-31: 최종 하루 3회 구현의 로컬 검사 결과와 Terraform 재검사 결과를 기록했어요.
