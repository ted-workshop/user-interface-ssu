# 의사결정 기록

"왜 이렇게 만들었지?"라는 질문에 당시 문제·대안·근거를 찾아 답하기 위한 기록이에요.
2026-10-20 사용자 요청으로 시작했어요. 사용자는 모든 의사결정을 문서화하고,
앞으로의 판단과 제안도 근거를 갖춰 설명하도록 요청했어요.

저장소 안의 Markdown을 사용해 코드와 함께 변경 이력을 검토하고 링크할 수 있게 해요.
별도 서비스나 문서 생성 도구는 추가하지 않아요. 채팅이나 PR에만 이유를 남기면 흩어지므로
판단의 근거는 이곳에 모으고 작업·PR에서 연결해요. 이 기록을 의사결정 기록, ADR이라고 불러요.

## 팀에 공유할 때

문서 공유 작업은 팀원이 GitHub에서 기록 본문을 열 수 있는지 확인한 뒤 완료로 표시해요.
관련 이슈에 원격 목차와 PR 링크를 남기고, PR 브랜치에서 읽을 수 있는 상태와
`main`에 반영된 상태를 구분해요. 로컬 파일 작성이나 구두 설명만으로 저장소 반영을 완료했다고 적지 않아요.

## 무엇을 남기나요?

구조·기능·API·DB·라이브러리·UI·운영·비용·보안·검증 등 모든 의사결정을 남겨요.
큰 구조 선택뿐 아니라 상태값, 재시도 방식, 조회 방법 같은 세부 판단도 이유를 찾을 수 있어야 해요.
같은 문제의 세부 판단은 한 기록에 묶고 코드·테스트·명세를 연결해요.
이미 정한 방식을 그대로 적용한다면 새 결정을 만들지 않고 해당 기록이나 기존 규칙을 연결해요.

기존 기록을 먼저 읽고, 새로 선택할 때는 [템플릿](template.md)을 복사해 다음 번호로 작성해요.
파일명은 `NNNN-short-description.md`를 사용하고, 목차에 상태와 날짜를 함께 추가해요.
제안할 때부터 기록하고, 채택 근거는 사용자 승인인지 승인 범위 안의 자율 판단인지 명시해요.
문서 작성은 이미 승인한 작업에 매번 새 승인을 요구하는 절차가 아니에요.

## 근거를 어떻게 설명하나요?

- 문제와 현재 동작을 먼저 적고 사용자 요구나 관련 코드·명세를 연결해요.
- 선택지별 장점·비용·한계와 추천한 이유를 적어요. 대안을 채택하지 않은 이유도 남겨요.
- 확인한 사실, 그 사실에서 도출한 판단, 가정과 미검증 항목을 구분해요.
- 근거는 관련 파일·심볼·커밋·테스트 명령·측정 결과 또는 공식 문서로 연결해요.
  요금·한도처럼 바뀔 수 있는 자료에는 확인 날짜와 적용 버전·환경을 적어요.
- 검증 방법과 실제 결과를 구분해요. 계산 예시·예상 트래픽·mock은 실측이나 공급자 검증이 아니에요.
- 어떤 증거가 나오면 결정을 바꿀지 구체적인 재검토 조건을 적어요.

사용자와 리뷰어가 제기한 반론에는 날짜, 반론, 답변과 근거, 결론을 남겨요.
반론에 답할 근거가 없으면 미해결로 적고, 잘못된 판단이면 수정하거나 새 결정으로 대체해요.
출처만 나열하지 않고 그 자료가 이 선택을 어떻게 뒷받침하는지 설명해요.
비밀값과 개인 계정 정보는 기록하지 않아요.

## 상태와 변경 이력

| 상태 | 의미 |
| --- | --- |
| 제안 | 선택지를 검토 중이에요. 확정이나 구현 완료를 뜻하지 않아요. |
| 확정 | 현재 따를 결정이에요. 확정 근거와 날짜를 남겨요. |
| 기각 | 채택하지 않은 제안이에요. 이유를 보존해요. |
| 대체 | 새 결정으로 바뀐 기록이에요. 새 기록과 서로 연결해요. |

확정한 기록의 당시 문제·대안·근거와 확정 이력을 보존해요.
결정을 바꿀 때는 새 기록에 변경 이유를 쓰고 이전 기록의 상태를 대체로 바꿔 양쪽을 연결해요.
오탈자·출처 보완·검증 경과는 같은 문서에 날짜와 함께 갱신할 수 있어요.
검증이 끝나지 않은 부분은 상태를 추측하지 않고 미검증으로 남겨요.
