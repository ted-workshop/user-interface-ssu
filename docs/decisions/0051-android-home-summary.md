# ADR-0051: 홈 현황과 영상 요약을 기존 API에 연결해요

- 상태: 확정
- 작성일: 2026-11-25
- 확정 근거: 사용자가 재운님 담당의 남은 GitHub 작업을 실행하도록 요청했어요. #28 범위 안에서 구현 방법을 판단했어요.
- 관련 기록: [ADR-0038](0038-android-foundation.md), [ADR-0039](0039-android-feature-packages.md), [ADR-0024](0024-direct-summary-http.md), [ADR-0046](0046-android-report-library.md), [API 계약](../api-contract.md).
- 구현·검증 상태: 홈·요약 화면 구현과 JVM·lint·APK 빌드 검사를 통과했어요. 기기 시나리오와 스크린샷은 아직 확인하지 못했어요. 실제 공급자·운영 배포는 이 작업에서 검증하지 않아요.

## 문제와 현재 상태

main `0758c74`에는 리포트 목록·상세가 있지만 홈·영상 요약 탭은 제목만 보여요.
[#28](https://github.com/ted-workshop/user-interface-ssu/issues/28)의 URL 접수 → 진행 → 완료 → 리포트 읽기를 이어야 해요.
이전 대화의 로컬 작업본은 현재 환경과 원격 브랜치에서 확인하지 못해, 최신 main에서 구현했어요. 이전 검사 결과를 이번 변경의 근거로 쓰지 않아요.

## 결정

- `home/`은 `GET /v1/dashboard`의 최근 리포트 5개와 개인 채널·요약·발송 현황을 표시해요. 홈을 여는 것만으로 채널 확인이나 요약을 접수하지 않아요.
- `채널 지금 확인`은 명시적 버튼으로 POST 한 번을 보내요. 이후 GET과 `nextCheckId`로 같은 묶음을 따라가고, 채널별 성공·실패를 누적해요. 확인 완료와 리포트 생성 완료를 구분해요.
- `summary/`은 영상 URL 검증·접수, 최근 요청 20개씩 조회, 개별 상태 조회, 서버가 허용하는 명시적 분석 재시도를 제공해요. 새 접수와 `attempt`를 보내는 재시도는 자동으로 실행하지 않아요.
- 상태 조회는 정상 5초, 실패하면 5·10·20·30초와 최대 500ms jitter로 늦춰요. `Retry-After` 전에는 수동 조회도 전송하지 않아요. 화면이 보이지 않으면 예약 조회를 취소해요.
- 접수 응답이 불명확하면 요청 목록 GET으로 같은 영상의 접수 여부를 확인해요. 분석 재시도 응답이 불명확하면 현재 요청 GET으로 갱신한 뒤에만 재시도를 허용해요.
- Activity 범위 ViewModel이 회전·탭 이동 중 요청을 유지해요. 프로세스 복원에는 선택한 자원 ID만 저장하고, 서버에 소유권을 다시 확인해요. 개인 본문·토큰·입력 URL을 별도 디스크 파일에 저장하지 않아요.
- 공통 세션 변경과 요청 세대를 대조해 이전 계정 응답을 버려요. 홈·요약에서 상세를 열면 공통 back stack으로 돌아오고, 다른 탭을 누르면 이 상세 경로를 정리해요.
- 화면은 기존 Color Tokens·XML·View Binding을 사용해요. 키보드의 아래 여백도 공통 화면에서 처리해 입력·버튼을 가리지 않게 해요.

## 근거와 대안

- 실제 `dashboard.ts`, `summary-requests.ts`, `channel-checks.ts`와 [API 계약](../api-contract.md)을 대조했어요. 새 API·DB·공급자 호출 방법을 추가할 필요가 없어요.
- Fragment 안에서 POST를 관리하면 회전 때 중복 제출·응답 유실 위험이 있어 기존 lifecycle ViewModel을 사용해요. WorkManager나 별도 백그라운드 서비스를 추가하면 서버가 이미 수행하는 작업과 책임이 겹치므로 쓰지 않아요.
- 모든 요청을 자동 재접수하면 일일 상한과 결과 불명 정책을 어겨요. 조회 재시도와 분석 재시도를 분리하고, 서버의 `retryable`과 관찰한 시도 번호를 따라요.
- #28 목업에는 영상 제목·썸네일·길이가 있지만 요청 API는 해당 필드를 주지 않아요. 진행 카드에는 정규화한 실제 URL을 표시하고, 최근 리포트에는 서버가 준 제목·채널명을 표시해요. 임의 제목·길이·진행률은 만들지 않아요.
- 날짜는 API가 준 UTC임을 표시해요. 마지막 확인 시각을 이번 요약 완료 시각으로 해석하지 않아요.

## 가정·한계와 영향

- #27 계정·채널 구현과 #29 모음·댓글 파일을 바꾸지 않아요. 최근 리포트와 완료 요청은 기존 상세 진입점을 재사용해요.
- 같은 계정의 요청이 오래된 페이지에 있으면 `요청 더 보기`로 찾아요. 앱 시작 때 모든 페이지를 자동으로 읽지 않아요.
- 채널 확인 POST가 응답 없이 끝나면 ID를 알 수 없으므로 자동 재접수하지 않아요. 사용자가 다시 누르면 서버의 진행 중 확인 재사용 규칙을 적용해요.
- 메일 `sent`는 SMTP 접수이며 실제 받은편지함 도착이 아니에요. 실제 메일 앱 검증 #88과 운영 배포는 별도예요.
- API·DB·Android 의존성 버전은 변경하지 않아요. #28 전체 완료는 실제 기기/에뮬레이터 검증이 끝난 뒤 판단해요.

## 검증과 재검토 조건

- JVM: URL 정규화·다른 호스트/자격증명/채널/여러 URL 거부, 정상·실패 간격과 `Retry-After`를 검사해요.
- `HomeSummaryFlowTest`: 기기 내부 MockWebServer로 홈 실패/복구, 접수 1회, 회전·탭 왕복, 완료 상세·뒤로 가기, 조회 실패·background 중 polling 중지, 관찰한 `attempt` 재시도, 접수 응답 유실 후 GET 복구, 로그아웃, 채널 확인 연속 작업을 검사하고 화면을 캡처해요.
- MockWebServer 검사는 앱 동작 검증이며 실제 Gemini·Gmail 성공 증거가 아니에요.
- API에 요청 제목·썸네일이 추가되거나 여러 요청의 실시간 동시 진행 표시가 필요해지면 화면 모델을 재검토해요.

## 검증 이력

- 2026-11-25: `bun scripts/android.ts check`의 Spotless·lintDebug·JVM 39개·디버그 APK 빌드가 통과했어요. `:app:assembleDebugAndroidTest :app:assembleRelease`도 통과했어요.
- Bun 1.4.4, Gradle Wrapper 9.6.0, Android SDK 37.0을 사용했어요. 실행 환경의 JDK는 Temurin 25.0.5.1+2이며, 저장소의 버전 설정은 바꾸지 않았어요. 고정 JDK의 검증은 PR CI에서 다시 확인해야 해요.
- API 37.0 / emulator 37.3.10에서 실행을 시도했지만, 환경에 `/dev/kvm`이 없고 소프트웨어 에뮬레이션도 부팅 완료 전에 종료됐어요. `HomeSummaryFlowTest`는 컴파일만 확인했으며 기기 테스트·화면 캡처 통과로 보고하지 않아요. 실제 기기/하드웨어 가속 AVD에서 `docs/development.md`의 명령으로 이어가야 해요.
- `git diff --check`와 관련 링크·담당 경로를 확인했어요. 실제 Gemini·SMTP 호출, 운영 배포는 수행하지 않았어요.

## 반론과 변경 이력

- 2026-11-25: 현재 계약으로 동작하는 홈·요약 흐름을 우선 연결하고, 공급자 검증과 목업에만 있는 필드는 구분했어요.
- 2026-11-25: #90이 반영된 main `df64d45`에 맞춰 상세 뒤로 문구 충돌을 정리했어요. 모음 이름으로 돌아가는 문구는 유지하고, 홈·요약 기기 시나리오의 닉네임·댓글 조회 응답을 새 상세 구성에 맞췄어요. 기기 실행은 여전히 미검증이에요.
