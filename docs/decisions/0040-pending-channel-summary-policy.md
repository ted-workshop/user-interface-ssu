# ADR-0040: 수신 주소가 없는 대기 요약은 재확인까지 보류해요

- 상태: 확정
- 작성일: 2026-11-21
- 확정일과 근거: 2026-11-21, 담당자 99eadb의 API 마무리 요청 범위에서 PR #46의 미해결 피드백을 검토하고 기존 동작을 유지하기로 판단했어요.
- 관련 기록: [ADR-0030](0030-channel-settings-http.md)의 개인 설정, [ADR-0031](0031-channel-check-execution.md)의 자동 접수,
  [ADR-0020](0020-shared-analysis-and-report-permissions.md)의 공통 분석, [ADR-0037](0037-channel-report-delivery.md)의 발송 대상을 적용해요.
  기존 확정 결정을 대체하지 않고, 주소 삭제 뒤 이미 접수된 요청의 처리 경계를 명시해요.
- 구현·검증 상태: 기존 실행기·DB 트리거를 유지하고 설정 HTTP와 실제 로컬 D1을 연결하는 회귀 검사 7개를 추가했어요.
  `mise run api:check`가 통과했어요. 원격 배포·Cron·실제 공급자 호출은 이번 검증 범위에 포함하지 않아요.

## 문제와 현재 상태

[PR #46의 리뷰](https://github.com/ted-workshop/user-interface-ssu/pull/46#discussion_r4478714486)는
마지막 수신 주소를 삭제한 뒤 `queued`로 남은 채널 요약을 `recipient_inactive`로 종료할지,
주소가 다시 확인될 때까지 보류할지 정하고 테스트로 고정하도록 요청했어요.
#14의 신규 접수 차단 검사만으로는 이미 접수된 요청의 재개·공통 분석 완료·소급 발송 여부를 확인할 수 없어요.

`jobs/analysis.ts`의 `eligibleRequest`·`claimAnalysis`는 현재 활성 구독과 본인의 확인된 주소를 요구해요.
`0003_shared_reports.sql`의 `recipient_stop`은 대기·실패 발송만 취소하고, `subscription_stop`은
그 구독의 대기 요약도 `failed / channel_inactive`로 끝내요. 두 설정 변경은 효과가 달라요.

## 결정

- **마지막 확인 주소 삭제:** 이미 접수된 채널 요청은 `queued` 상태와 기존 시도 수를 유지해요.
  다른 실행 가능한 요청이 없다면 분석 작업을 점유하거나 공급자를 호출하지 않아요.
  주소를 단순히 추가하거나 다른 계정이 주소를 확인해도 실행하지 않아요.
  본인의 새 주소 확인과 원래 구독의 활성 상태가 모두 충족되면 같은 작업을 실행할 수 있어요.
  같은 이메일을 재등록하든 다른 이메일을 등록하든 확인 절차를 다시 거쳐요.
- **확인 주소가 남아 있는 경우:** 한 주소를 삭제해도 다른 확인 주소가 있으면 실행할 수 있어요.
  새 리포트 저장 시점의 살아 있는 확인 주소만 발송 대상이에요.
- **채널 중지·삭제:** 기존 트리거대로 대기 요약을 `failed / channel_inactive`로 끝내요.
  주소 재확인·구독 재개·같은 채널 재등록으로 이전 요청을 자동 재개하지 않아요.
  재등록은 별도 구독 UUID·첫 기준을 사용하고 옛 요청과 연결하지 않아요.
- **공통 분석이 다른 요청 때문에 완료된 경우:** 다른 계정의 직접 요약처럼 실행 가능한 요청이 있으면
  같은 영상·생성 설정의 분석은 진행할 수 있어요. 보류된 `queued` 요청에도 결과와 개인 열람 권한을 연결해요.
  결과 저장 당시 확인 주소가 없는 사용자의 발송 행은 만들지 않아요.
  결과 저장 뒤 주소를 확인해도 과거 리포트를 소급 발송하거나 다시 분석하지 않아요.
- **이미 취소된 발송:** 삭제 전 주소 UUID에 연결된 `cancelled / recipient_inactive` 이력은 그대로 남아요.
  같은 이메일을 다시 확인해도 취소 발송을 되살리거나 새 발송 행으로 바꾸지 않아요.
- 새 상태값·실패 코드·테이블·실행기 분기를 추가하지 않아요. 설정의 계정 격리와 위 경계를
  `channel-settings.test.ts`의 설정 HTTP·요약 실행·발송 점유 검사로 고정해요.

## 근거와 대안

현재 실행기는 이미 접수한 요청과 공통 분석을 분리해요. 주소 교체 때문에 아직 실행하지 않은 요청을
실패시키면 사용자가 재확인 후에도 영상을 다시 요청해야 하고, 주소 삭제가 공통 작업 실패로 번지지 않게
별도 상태 전이를 설계해야 해요. 기존 보류 동작을 유지하면 새 호출·재접수 없이 확인된 대상에게만 이어갈 수 있어요.

대안인 즉시 `recipient_inactive` 실패는 대기 목록이 명확해지는 장점이 있지만,
현재 이 코드는 발송 취소를 나타내고 분석 재시도는 일시 오류만 허용해요. 이를 요약 실패에도 적용하려면
재개 API와 사용자 안내를 함께 바꿔야 하므로 이번 설정 API 마무리에서는 채택하지 않아요.
주소 복구 때 과거 리포트를 소급 발송하는 대안은 ADR-0037의 저장 시점 대상 고정과 맞지 않아 채택하지 않아요.

## 가정·한계와 영향

- 주소를 확인하지 않으면 대기는 기한 없이 유지돼요. 별도 만료·자동 실패·보류 사유 응답은 추가하지 않아요.
- 보류는 해당 요청이 새 실행을 시작할 수 없다는 뜻이에요. 공통 작업 자체의 전역 중단을 의미하지 않아요.
  이미 시작한 분석 결과를 보존하는 기존 정책도 유지해요.
- 마이그레이션·의존성·제품 실행 코드 변경은 없어요. API 계약에는 주소 보류와 채널 종료의 차이를 보완해요.
- 로컬 SMTP 전송·YouTube·Gemini 결과는 fixture예요. 실제 메일 도착·원격 Cron·운영 배포 검증은 #17에 남아요.

## 검증과 재검토 조건

- 새 회귀 검사 7개는 같은/다른 이메일 재확인, 타 계정 확인으로 재개 불가, 남은 확인 주소,
  채널 중지·재개와 삭제·재등록, 다른 계정의 공통 분석 완료, 취소 발송 보존을 확인해요.
  실제 migration을 적용한 D1에서 동작하고 재확인은 토큰 발급·소유자 확인·일회 소비 HTTP를 통과해요.
- 실행기 점유 전후의 요청 상태·시도 수·리포트·수신 대상과 발송 점유 결과를 확인해요.
  공급자 요청 생성이나 실제 공급자 성공을 이 검사로 주장하지 않아요.
- 2026-11-21 Linux·Bun 1.4.4·Node 24.22.1에서 `mise run api:check`가 통과했어요.
  workerd 459개(설정 HTTP 24개 포함), Bun tools 16개, 저장소 스크립트 51개와
  포맷·타입·Worker dry-run을 확인했어요. `git diff --check`도 통과했어요.
- 장기 보류 요청의 누적·사용자 혼동이 관찰되거나 자동 만료·명시적 취소가 요구되면
  보류 상태 표시와 재개/만료 정책을 새 기록에서 함께 검토해요.

## 반론과 변경 이력

- 2026-11-21: PR #46의 보류 대 즉시 실패 피드백에 답해 기존 보류 동작을 채택했어요.
  채널 중지·삭제는 주소 삭제와 달리 이미 대기 요약을 실패시키는 것을 DB 트리거에서 확인하고
  해당 차이와 공통 결과 재사용·소급 발송 금지까지 검증 범위에 포함했어요.
