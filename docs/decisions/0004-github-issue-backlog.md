# ADR-0004: GitHub 이슈로 팀 작업과 선행 관계를 관리해요

- 상태: 확정
- 작성·확정일: 2026-10-20
- 확정 근거: 사용자가 다음 작업을 목록화해 GitHub 이슈에 올리고 다른 팀원도 추가할 수 있게 요청했어요.
  추적 이슈·하위 작업·우선순위·선행 관계의 구체적인 구성은 그 요청 범위에서 정한 판단이에요.
- 관련 기록: [ADR-0001](0001-workers-d1-free-tier.md), [ADR-0003](0003-shared-modules-sync-async.md),
  [팀 기여 가이드](../../CONTRIBUTING.md)
- 구현·검증 상태: 2026-10-20에 [API 작업 추적 이슈 #2](https://github.com/ted-workshop/user-interface-ssu/issues/2)와
  하위 작업 15개를 등록하고 본문·라벨·열린 상태·담당 미지정·상위 관계·선행 관계를 확인했어요.
  이슈의 현재 진행 상태는 GitHub에서 확인해요. API 구현·테스트·배포는 미완료예요.

## 문제와 현재 상태

합의한 서버 구조를 구현하려면 팀원이 채팅 없이도 할 일과 완료 기준을 확인할 수 있어야 해요.
2026-10-20 조회 시 저장소의 기존 이슈는 없었고, 기준 커밋은
`8245e24f0b74ac722c08dd3b594062f6a1f0b975`였어요.
[현재 API](../../apps/api/src/app.ts)는 health·공통 오류 응답까지예요.
실제 인증·영상 처리·영구 저장·메일·자동화는 아직 검증하지 않았어요.

이미 [기능 제안 양식](../../.github/ISSUE_TEMPLATE/feature.yml)과
[작업 양식](../../.github/ISSUE_TEMPLATE/task.yml)이 있어요.
개별 작업의 이유·범위·완료 기준을 같은 형식으로 적고 선행 작업을 연결할 수 있어요.

## 결정

- 실행할 작업의 범위·진행 상태·담당·선행 관계는 GitHub 이슈에서 관리해요.
  API 완성의 추적 이슈에 하위 작업을 연결하고, 본문에도 이슈 번호와 완료 기준을 남겨요.
- 기반·공급자 검증 → 직접 요약 시연 → 채널 자동화 → 배포된 API의 실제 경로 검증 순서로 묶어요.
  기능별 선행 관계를 연결하고 독립적인 조사·계약 초안은 먼저 진행할 수 있게 해요.
- 기존 영역 접두어·우선순위·라벨·양식을 사용해요. 새 보드·상태 도구·기한·자동 배정은 추가하지 않아요.
- 팀원은 맡을 작업에 댓글로 착수 의사와 범위를 남기고 권한이 있으면 자신을 담당자로 지정해요.
  빠진 기능·Android 화면·문서 작업도 기존 양식으로 추가하고 상위 이슈나 관련 API 작업을 연결해요.
- 지속해서 확인할 선택 근거는 이 폴더의 기록에 남겨 이슈·PR에서 연결해요.
  전체 작업 목록과 상태를 별도 Markdown에 복제하지 않아요.

## 근거와 대안

[기능 명세](../qletter/02-functional-spec.md)의 F-01~F-04는 직접 요약과 저장 결과 읽기를,
F-05~F-08은 채널 설정·새 영상 확인·메일 복구를 요구해요.
[PRD](../qletter/01-prd.md)의 핵심 시연 흐름을 먼저 완성하고 자동화를 이어 붙이면
실제 사용자 결과로 작업을 확인할 수 있다고 판단해요. 홈 현황은 PRD의 보조 기능으로 따로 관리해요.

Gemini·메일의 실제 지원 범위가 미검증이므로 공급자 검증을 API 계약과 기능 구현보다 앞에 둬요.
가짜 성공 결과에 맞춰 계약을 정하는 위험을 줄이려는 판단이며, 이 순서가 개발 시간을 얼마나
줄이는지 측정한 결과는 아니에요. Workflows는 [ADR-0002](0002-workflows-for-background-jobs.md)의
제안 상태를 유지하고 실행 기반 작업에서 비교·검증해요.

하나의 체크리스트만 쓰면 작성은 빠르지만 기능별 완료 기준·토론·담당·의존성을 따로 관리하기 어려워요.
반대로 엔드포인트마다 이슈를 만들면 작은 팀이 조율할 항목이 많아져요.
따라서 팀원이 한 기능 흐름을 맡고 검증할 수 있는 단위로 나눠요.
실제 크기가 너무 크면 담당자가 범위와 하위 작업을 조정해요.

별도 문서·보드도 작업 순서를 표현할 수 있어요. 다만 사용자가 GitHub 이슈를 요청했고
저장소에 기존 양식이 있으므로, 같은 상태를 여러 곳에 갱신하는 부담을 만들 이유가 없다고 판단해요.
이슈 본문에는 지속적인 변경 이유를 모두 쌓기보다 관련 의사결정 기록을 연결해요.

## 가정·한계와 영향

담당자·기한·예상 작업 시간은 정하지 않았어요. 우선순위와 묶음은 현재 명세와 미구현 상태를 기준으로
정한 초기 계획이며 제품 정책이나 구현 완료의 승인이 아니에요.
API 중심 목록이므로 전체 Android 제품의 할 일을 모두 열거한 것으로 보지 않아요.
누구에게도 작업을 자동 배정하거나 별도 메시지를 보내지 않았어요.

팀원이 이슈를 만들고 담당·상위 관계를 변경할 수 있는 범위는 자신의 저장소 권한에 따라요.
연결 권한이 없으면 추적 이슈에 링크를 남겨 관리자가 추가할 수 있게 안내해요.
문서의 원격 공유 링크와 저장소 반영 상태는
[문서 공유 작업 #3](https://github.com/ted-workshop/user-interface-ssu/issues/3)에서 확인해요.

## 검증과 재검토 조건

원격에서 본문·제목·우선순위·라벨·열린 상태·담당 미지정·상위 이슈·선행 관계를 다시 읽어 확인해요.
새 이슈가 중복 생성되지 않았는지, 선행 관계가 순환하지 않는지, 링크가 현재 기준 코드와 연결되는지도 확인해요.
실제 기능은 각 이슈의 완료 기준과 검증으로 따로 입증해요.
2026-10-20 문서·이슈 정리에서는 런타임 변경이 없어 앱 검사를 생략했어요.

2026-10-20 원격 재조회에서 추적 이슈 1개와 하위 작업 15개의 제목·본문·라벨·상위/선행 관계가
준비한 내용과 일치하고 모두 열린 상태·담당 미지정임을 확인했어요. 중복 생성은 없었어요.

팀원이 한 이슈를 독립적으로 끝내기 어렵거나 선행 관계 때문에 불필요하게 기다리면 범위를 다시 나눠요.
실제 공급자·비용·제품 정책이 바뀌면 영향을 받는 계약과 작업을 갱신해요.
다른 곳에 상태가 중복돼 실제 진행을 알기 어려워지면 이슈를 기준으로 다시 맞춰요.

## 반론과 변경 이력

- 2026-10-20: 사용자의 GitHub 이슈·팀 참여 요청에 맞춰 관리 방식을 정했어요.
  작업 묶음과 우선순위는 이후 팀 논의와 검증 결과에 따라 수정할 수 있어요. 별도의 반론은 아직 없어요.
- 2026-10-20: 사용자가 마일스톤 단위로 묶자고 요청했어요. 기존 이슈·선행 관계를 유지하고
  [ADR-0005](0005-outcome-milestones.md)에 목표별 묶음과 완료 기준의 근거를 추가했어요.
- 2026-10-23: 문서가 로컬 미커밋 상태로 남아 있음을 확인하고 원격 공유 작업을 재개했어요.
  이슈 등록 당시의 확인 결과와 현재 진행 상태를 구분하고, 공유 링크는 #3에서 안내해요.
