# ADR-0037: 채널 리포트 발송 행을 리포트 저장과 함께 만들고 주소별로 재시도해요

- 상태: 확정
- 작성일: 2026-11-13
- 확정일과 근거: 2026-11-13, 사용자의 #15 구현 시작 요청과 이슈의 완료 기준 범위 안에서 자율 판단했어요.
- 관련 기록: [ADR-0022](0022-d1-scheduled-jobs.md)·[ADR-0023](0023-background-runner-readability.md)의 D1 발송 실행기,
  [ADR-0012](0012-gmail-smtp-email-foundation.md)의 SMTP 발송, [ADR-0018](0018-api-contract-and-policies.md)의 발송 정책,
  [ADR-0019](0019-d1-product-schema.md)의 발송·수신 주소 제약, [ADR-0020](0020-shared-analysis-and-report-permissions.md)의 개인 권한,
  [ADR-0031](0031-channel-check-execution.md)의 채널 자동 요약을 적용해요.
- 구현·검증 상태: 리포트 저장 시 발송 행 생성, 리포트별 발송 목록, 주소별 재시도 HTTP를 구현하고 로컬 workerd 검사를 통과했어요.
  실제 SMTP 수신·도착과 원격 Cron·배포 환경은 확인하지 않았어요.

## 문제와 현재 상태

[#15](https://github.com/ted-workshop/user-interface-ssu/issues/15)는 채널 자동 요약의 결과를 수신 주소별로 보내고,
메일 실패가 리포트 손실이나 영상 재분석으로 이어지지 않게 해요. [기능 명세](../qletter/02-functional-spec.md) F-07과
[API 계약](../api-contract.md)은 채널 자동 요약만 발송하고, 리포트 저장 시점의 확인된 주소를 발송 대상으로 고정하며,
실패 주소만 재시도하고 중지·삭제된 채널·주소의 대기 발송을 멈추도록 정해요.

#10에서 `deliveries`·`delivery_attempts` 표, SMTP 실행기, 임시 오류 재시도, `enqueueDelivery`·`retryDelivery` 함수를 만들었어요.
하지만 채널 리포트가 저장될 때 발송 행을 만드는 호출부와 사용자 HTTP가 없어, 리포트를 저장해도 메일이 만들어지지 않았어요.
#14는 채널 확인과 분석 접수까지만 연결했어요.

## 결정

- 채널 리포트를 저장하는 `completeAnalysis`의 D1 batch에 발송 행 생성을 함께 넣어요. 리포트·개인 권한·요청 완료·발송 행을
  한 트랜잭션으로 저장해, 리포트만 저장되고 발송 행이 사라지는 중간 상태를 만들지 않아요.
  SMTP 호출은 이후 Cron 실행기에서 별도로 하므로 메일 실패가 리포트 본문이나 완료 상태를 바꾸지 않아요.
- 발송 대상은 **리포트 저장 시점에 확인된 주소**예요. `recipients.verified_at IS NOT NULL AND verified_at <= reports.created_at`과
  살아 있는 주소, 활성 구독, 개인 열람 권한을 같은 SQL에서 확인해요. 리포트 저장 뒤에 추가·확인한 주소와 직접 요약에는
  발송 행을 만들지 않아 과거 결과를 소급 발송하지 않아요.
- 한 리포트에 주소별 발송 행을 하나씩 만들고, 기존 `(user_id, report_id, recipient_id)`·`(user_id, report_id, recipient_email)`
  unique와 `NOT EXISTS`로 중복을 막아요. 이미 완료된 공통 리포트를 나중에 요청해 재사용하는 경우에는 발송 행을 만들지 않아요.
- D1 batch 안에서 행마다 UUID를 만들기 위해 SQLite 식으로 UUID v4 형식 문자열을 생성해요(`uuidSql`). 애플리케이션이
  미리 ID를 만들려면 대상 행을 먼저 조회해야 하고 그 사이 주소·구독이 바뀔 수 있어, 저장과 같은 문장에서 ID를 만들어요.
- `GET /v1/reports/{id}/deliveries`는 개인 열람 권한이 있는 사용자에게만 주소별 `id`, `email`, `status`, `attempt`,
  `failureCode`, `retryable`을 공통 `limit`·`cursor`로 돌려줘요. 권한이 없으면 같은 `404`이고, 취소된 발송 이력도 함께 보여줘요.
- `POST /v1/deliveries/{id}/retry`는 `{"attempt":N}`을 받아 기존 `retryDelivery`의 compare-and-set 규칙을 적용해요.
  `temporary` 실패만 `failed`에서 `queued`로 되돌리고, 접수하면 `202`, 이미 접수·재사용이면 `200`, 그 외 상태·시도 번호는
  `409 RETRY_NOT_ALLOWED`, 다른 사용자의 발송은 `404`예요. 재시도는 저장된 본문만 사용하고 Gemini를 다시 호출하지 않아요.
- 중지·삭제는 새 결정을 추가하지 않고 기존 `subscription_stop`·`recipient_stop`·`permission_remove` 트리거와
  실행기의 발송 직전 재검사를 그대로 사용해 대기·실패 발송을 `cancelled`로 바꿔요. `ambiguous`는 자동 재시도·사용자
  재시도 대상이 아니며 공급자 증거로 확인하기 전에는 `sent`로 바꾸지 않아요.
- 발송 상태·재시도 한도·lease·응답 유실 처리는 #10의 실행기를 유지해요. 새 작업 큐·발송 재설계·범용 메일 API는 추가하지 않아요.

## 근거와 대안

D1 batch는 순차 SQL을 하나의 트랜잭션으로 처리하고, 리포트 저장은 이미 시도·보고서·권한·요청 완료를 한 batch로 묶어요.
발송 행을 같은 batch에 넣으면 "리포트는 저장됐지만 발송 행은 없는" 상태가 없고, 발송 행 생성이 실패하면 리포트 저장도
함께 rollback돼 부분 완료를 만들지 않아요. SMTP 실패는 이후 단계라 리포트·요청 상태와 분리돼요.

대안으로 실행기가 리포트 완료 뒤 별도 호출로 발송 행을 만드는 방법은 구현이 단순하지만, 완료 저장과 발송 행 생성 사이에
Worker가 종료되면 발송이 영구 누락돼요. 누락 복구용 정기 조회는 오래된 리포트나 배포 전 리포트까지 다시 발송할 위험이 있어
채택하지 않았어요. 채널 확인 시점에 발송 행을 만드는 방법은 아직 리포트가 없어 불가능해요.

발송 목록을 리포트 하위 경로에 둔 이유는 권한 기준이 리포트의 개인 열람 권한과 같기 때문이에요. 재시도는 발송 ID로
직접 다루되 세션 사용자로 제한했어요. 별도 발송 조회 전용 자원·집계 API는 만들지 않았어요.

## 가정·한계와 영향

- 리포트 저장 시각과 주소 확인 시각이 같은 초에 겹치면, 그 초에 확인된 주소가 대상에 포함될 수 있어요. 시각 단위는 UTC 초예요.
- 발송 행 생성은 리포트 저장 batch에 포함돼요. 발송 행 INSERT가 DB 오류로 실패하면 리포트 저장도 rollback되고,
  분석 시도는 다음 복구에서 결과 불명으로 처리될 수 있어요. 조건을 SELECT와 트리거에서 같게 확인해 논리적 불일치로는
  실패하지 않게 했지만, DB 전체 장애는 이 경계에서 구분하지 않아요.
- 이미 완료된 리포트를 재사용하는 요청(다른 사용자가 같은 영상을 나중에 채널에서 발견)은 발송 행을 만들지 않아요.
  그 사용자는 앱에서 리포트를 읽을 수 있지만 메일은 받지 않아요. 과거 결과 소급 발송을 막는 계약을 따른 결과예요.
- 실제 SMTP 수신함 도착, 스팸 분류, 공급자 중복 제거는 확인하지 않았어요. `sent`는 SMTP 접수이고 도착·열람이 아니에요.
  같은 발송 UUID에서 만든 Message-ID도 공급자의 중복 제거를 보장하지 않아요.
- 발송·시도 행은 정리 정책 없이 누적돼요. 사용자가 주소를 삭제해도 이력은 남아요.
- Android 화면과 원격 배포는 이 범위가 아니에요. 실제 메일 도착과 배포 환경 발송은 미검증이에요.

## 검증과 재검토 조건

- `mise run api:check`가 통과했어요: workerd 448개, Bun tools 16개, 저장소 스크립트 51개, 타입·포맷·Worker dry-run.
- `deliveries.test.ts` 10개는 채널 리포트 저장 시 주소별 발송 행 생성, 직접 요약·늦게 확인한 주소 제외,
  같은 영상을 요약한 다른 계정의 주소별 발송, 이미 완료된 리포트 재사용의 발송 없음, 일부 실패·재시도,
  채널 중지 시 취소, 다른 계정 접근 404, 발송 목록 pagination, 권한 회수 뒤 404, 발송 행 저장 실패 시
  리포트·권한 부분 저장이 없는지를 확인해요.
- 기존 `jobs.test.ts`의 발송 실행·임시 오류 재시도·ambiguous·설정 변경 취소 검사와 `reports.test.ts`의 발송 상태 계산도 통과해요.
- 실제 수신 주소의 메일 도착은 확인하지 않았어요. 승인된 테스트 주소와 SMTP 자격 증명이 필요해요.
- 재검토 조건: 실제 발송 누락·중복이 관찰되면 발송 행 생성 경계·정기 복구·공급자 중복 키를 다시 설계해요.
  리스트 조회가 느려지거나 발송 행이 많이 쌓이면 인덱스·보존 정책을 정해요. 재사용 리포트의 메일 미발송이 제품 기대와
  다르면 소급 발송 정책을 새 기록에서 다시 정해요.
