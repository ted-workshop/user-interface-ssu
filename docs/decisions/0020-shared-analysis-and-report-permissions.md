# ADR-0020: 보고서 하나를 사용자별 권한으로 공유해요

- 상태: 확정
- 작성일: 2026-10-28
- 확정일·근거: 2026-10-28, 전체 ERD 확인 후 사용자가 적용을 승인했어요. 공개 관리 주체는 미정으로 유지해요.
- 관련 기록: [ADR-0018](0018-api-contract-and-policies.md), [저장 기반 #8](https://github.com/ted-workshop/user-interface-ssu/issues/8),
  [공개·댓글 #23](https://github.com/ted-workshop/user-interface-ssu/issues/23),
  [모음 #24](https://github.com/ted-workshop/user-interface-ssu/issues/24)
- 구현·검증 상태: 계약과 0003_shared_reports.sql에 공통 모델을 구현했어요. 제품 HTTP·공급자·원격 검증은 별도예요.
  이 기록은 ADR-0018의 보고서·권한 계약을 대체해요. 인증·재시도·공급자 gate는 기존 정책을 유지해요. ADR-0019의 저장 모델도 대체해요. 0001·0002 파일은 보존해요.
- 구체화한 설계: [공통 보고서·접근 권한 ERD](../database-erd-proposal.md)예요.
- 전체 원본: [17개 테이블의 전체 ERD](../diagrams/qletter-full-erd-proposal.mmd)예요.

## 문제와 현재 상태

현재 제품 migration은 사용자마다 요청·보고서·본문을 만들어요. 앞선 수정안은 분석과 본문만
공유하고 사용자별 reports.id를 남겨, 같은 영상을 보는 사람들의 댓글이 여러 보고서로 나뉘었어요.
하나의 보고서와 댓글을 공유하려는 요구를 만족하지 못해 이 안을 철회해요.

#23의 회의 합의는 조회 권한 테이블을 조회·댓글 권한으로 확장하고 별도 공유 테이블을 추가하지
않는 방식이에요. 현재 migration에는 그 권한 기반도 없어요. 사용자별 활동·설정 보호와 공통
보고서 식별자를 분리해야 해요.

## 제안

- 공통 영상·생성 설정마다 analysis_jobs 하나와 완성된 reports 하나를 만들어요.
  reports에는 공통 본문·출처·성공 시도를 두고 개인 user_id·request_id는 두지 않아요.
  앞선 report_contents 테이블은 제거하고 reports에 합쳐요.
- summary_requests에는 사용자·생성 경로·구독·공통 작업을 둬요. A·B는 다른 개인 요청을 가지지만
  완료 시 같은 report_id를 받아요. 실행 중 공통 작업에 합류하거나 기존 보고서를 재사용해요.
- report_permissions의 개인 사용자 규칙으로 여러 계정이 같은 보고서에 접근·보관해요.
  보관함에서 제거할 때 본인 관계만 제거하고 보고서·다른 사람의 권한·댓글은 지우지 않아요.
- 같은 테이블의 authenticated 규칙은 로그인 사용자 전체에 적용해요. 별도 공유 테이블이나
  모든 계정에 대한 공개 권한 행 복제는 추가하지 않아요. 개인 규칙과 공개 규칙은 partial unique로
  각각 중복을 막고 NULL을 포함한 일반 unique의 중복 허용을 놓치지 않아야 해요.
- comments.report_id는 공통 reports.id를 참조해요. A·B가 같은 보고서에서 같은 댓글 목록을 봐요.
  비공개 댓글 조회·작성 금지와 본인 댓글만 삭제하는 #23 규칙은 유지해요.
- 채널 식별 정보와 개인 구독·시작 기준·주기·중지·삭제를 분리해요. A의 변경이 B를 중단하지 않아요.
  B의 최초 등록은 B의 시작 기준을 기록하며 A의 과거 보고서를 소급 발송하지 않아요.
- 메일 대상은 개인 요청·원래 구독·수신 주소로 판단해요. 같은 보고서를 써도 직접 요약은
  자동 메일을 만들지 않고 B의 자동 요청은 B의 확인된 주소에 발송해요.
  발송 중복 키에는 user_id를 포함해 다른 계정의 발송을 잘못 막지 않아요.

## 근거와 대안

2026-10-28 기존 PR #33의 [migration](https://github.com/ted-workshop/user-interface-ssu/blob/39da42bd2412ea400bd39d616498779b8df58191/apps/api/migrations/0002_product_schema.sql),
[API 계약](../api-contract.md)과 #23의 현재 본문을 확인했어요. 사용자는 같은 보고서에서
댓글을 함께 조회하는 요구를 확인했어요. 본문 공유만으로는 공통 보고서·댓글 식별자를 제공할 수 없어요.

사용자별 보고서는 독립적인 공개 설정을 유지하기 쉽지만 보고서와 댓글이 분산돼요.
공통 보고서와 사용자별 권한 관계는 보관·접근을 개별 관리하면서 보고서·댓글 ID를 통일할 수 있어요.
이를 위해 공통 보고서의 공개 관리 주체를 개인 보관 관계와 따로 정해야 해요.

최초 요청자에게 공통 보고서의 소유권과 전역 공개 전환 권한을 주면 구현은 단순해요.
다만 한 사람이 다른 사용자의 댓글 접근까지 철회할 수 있어 자동으로 그 권한을 부여하지 않아요.
본문만 분리하는 앞선 대안은 댓글 분산 문제를 해결하지 못해 채택하지 않아요.

## 가정·한계와 영향

공유 대상은 공개 영상·동일 생성 설정의 시스템 생성 보고서예요. 개인 프롬프트·메모·수신 주소를
공통 본문에 섞지 않아요. 접근 규칙을 통과하기 전에는 내부 보고서와 댓글·타인의 요청 이력을 보여주지 않아요.

공통 보고서는 독점적인 개인 작성자가 없어요. #23의 '작성자만 공개/비공개 전환'과 '작성자만
비공개 조회'는 이 모델에 맞게 수정해야 해요. 공개 관리 주체와 공개 철회 시 댓글 보존·삭제는
미확정이에요. 특정 사용자에게 전역 관리 권한을 자동으로 주거나 모든 보고서를 자동 공개하지 않아요.

#7·#8의 계약·저장 기반과 #12·#13·#14·#15·#23·#24의 보관·발송·권한 참조를 맞춰야 해요.
적용한 migration을 덮어쓰거나 원격 데이터를 변경하지 않아요. 기존 개인 제품 행은 생성 설정이 불명확하므로 자동 합치지 않으며 후속 migration은 그런 행이 있으면 실패시켜 보존해요. 실제 이관·복구와 권한 검증은
공개 정책을 확정한 구현에서 다뤄야 해요. 계약 확정과 제품 HTTP·공개 관리 기능 구현은 구분해요.

## 검증과 재검토 조건

문서에서는 사용자별 reports.id와 report_contents 이중 구조를 제거했어요.
아래는 로컬 D1 저장 검사 항목이며 실제 인증·제품 HTTP·공급자 성공의 증거는 아니에요.

2026-10-28 현재 #33 작업 트리에서 다음을 통과했어요.

- `mise run api:check`와 `mise run check`: workerd 120개 중 현재 DB 30개,
  Bun 도구 16개·공통 도구 49개, Android 포맷·Lint·단위 테스트·debug 빌드와
  두 Terraform root의 backend 없는 init·validate를 포함해요.
- 별도 Wrangler 로컬 persist에 0001·0002·0003을 적용하고 재실행의 `No migrations to apply`를 확인했어요.
  실제 SQL과 ERD의 17개 테이블·116개 열이 일치하고 FK 위반은 0개예요.
- 기존 본문이 있는 fixture에서 0003 실패·이력 rollback·본문 보존을, 빈 제품 스키마에서는
  기존 계정·세션·수신 주소·토큰 보존과 반복 적용을 검사했어요.
- 보관함 계획은 `permissions_library`와 보고서 PK 검색이에요. 빈 로컬 DB 보조 할당은
  385,024바이트예요. CLI의 meta는 duration만 제공해 미제공 읽기·쓰기 수치를 추정하지 않았어요.
- Bun 1.4.4·Node.js 24.22.1·Temurin 25.0.5+8을 mise 환경 변수로 선택했어요.
  다른 작업의 runtime 고정 파일을 복사하지 않았어요. 실제 공급자·원격 DB·기기 UI는 실행하지 않았어요.

전체 원본의 17개 테이블·116개 열·27개 논리 FK 관계를 대조했어요.
HTML 도식은 728px·390px에서 표시하고 전체·영역별 전환, 키보드 선택·열과 제약 조회를 확인했어요.
이는 문서·도식 검증이며 migration 실행이나 실제 API·공급자 사용을 검증한 것은 아니에요.

- A·B 같은 입력이 작업 1개·보고서 1개·개인 요청 2개·개인 접근 규칙 2개로 이어져요.
- A·B가 같은 report_id를 받고, B가 쓴 댓글을 A가 같은 목록에서 읽어요.
- A의 개인 관계 제거·구독 중지가 B의 접근과 공통 댓글을 손상하지 않아요.
- 공개되지 않은 보고서의 댓글 조회·작성을 거부하고 권한 없는 본문 조회를 막아요.
- A 직접 요청·B 자동 요청은 같은 보고서를 사용해도 B에게만 자동 메일을 만들어요.
- 응답 유실·재시도가 중복 보고서·메일을 만들지 않고 미확인 공급자 결과를 보존해요.

영상별 설정을 달리해도 댓글을 합치거나 개인 입력이 공통 본문에 포함되는 요구가 생기면
보고서·댓글의 버전 경계를 다시 검토해요. 기존 확정 결정을 대체할 때 범위와 검증 결과를 남겨요.

## 반론과 변경 이력

- 2026-10-28: 첫 수정안은 공통 본문과 개인 보고서를 분리했어요. 개인 공개 권한을 보존하려던
  선택이었으나 하나의 보고서·댓글 공유 요구를 만족하지 못했어요.
- 2026-10-28: 사용자 반론을 수용해 개인 reports.id와 report_contents 이중 구조를 철회했어요.
  공통 reports와 사용자별 접근 관계로 수정하고 전역 공개 관리 정책은 미확정으로 기록해요.
- 2026-10-28: 전체 ERD 요청에 맞춰 인증·설정·구독·분석·권한·댓글·발송의 17개 테이블,
  116개 열·27개 논리 관계를 하나의 원본으로 정리했어요. 복합 소유권·작업 일치와 실제 D1 검증은
  구현에서 확인할 조건으로 구분했어요.

- 2026-10-28: 전체 ERD 적용 승인을 반영해 확정했어요. 댓글 길이 1~2,000자와 공개 변경 API 보류를 같은 계약에 명시했어요.
