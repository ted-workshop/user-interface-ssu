# ADR-0022: D1 대기열과 예약 실행으로 분석·메일을 복구해요

- 상태: 대체
- 작성·확정일: 2026-10-30
- 확정 근거: 사용자의 기능 구현 시작 요청과 #10의 실행 방식 선택 범위 안에서 판단했어요.
- 대체일·근거: 2026-10-30, 사용자의 실행 플래그 제거 요청을 [ADR-0023](0023-background-runner-readability.md)에 반영했어요.
  아래는 최초 결정을 보존해요. D1 대기열·실행권·복구·재시도 규칙은 새 기록에서도 유지해요.
- 관련 기록: [ADR-0002](0002-workflows-for-background-jobs.md)의 Workflows 제안을 기각해요.
  [ADR-0003](0003-shared-modules-sync-async.md)의 실행 경계와
  [ADR-0020](0020-shared-analysis-and-report-permissions.md)의 공통 보고서 모델을 적용해요.
- 구현·검증 상태: D1 실행기·scheduled 핸들러·추가 migration과 로컬 장애 검사를 구현했어요.
  제품 HTTP·Android 연결·원격 배포·실제 공급자 성공은 이 기록의 완료 범위에 포함하지 않아요.

## 문제와 현재 상태

[#10](https://github.com/ted-workshop/user-interface-ssu/issues/10)은 앱 연결이 끊겨도 접수된 작업을 유지하고,
실행 전달 누락·반복 전달·중단에서 보고서와 메일을 중복 처리하지 않는 기반을 요구해요.
0003에는 작업·시도·결과·개인 접근 규칙이 있지만 실행권·호출 시작·예약 실행 코드는 없었어요.
Gemini 실제 성공 검증이 막혀 있어도 이 저장·복구 흐름은 외부 응답 fixture로 개발할 수 있어요.

## 결정

- `analysis_jobs`와 `deliveries`의 queued 행 자체를 대기열로 써요. 접수 후 별도의 메시지 발행은 없어요.
  Wrangler가 관리하는 1분 Cron 하나가 scheduled 핸들러를 호출해요. 한 번에 분석·메일을 각각 하나만 시작해요.
- 종류별 실행 중 작업도 하나로 제한해 중첩 Cron이 새 공급자 호출을 추가하지 못하게 해요.
  이는 실행 동시성 제한이고 Google 프로젝트 전체의 RPM·TPM·RPD 제한기는 아니에요.
- claim·개인 요청 전이·시도 생성은 D1 batch로 묶어요. 실행권의 무작위 token과 만료를 비교하고
  모든 후속 쓰기에서 같은 token을 확인해 이전 실행자가 호출하거나 결과를 덮어쓰지 못하게 해요.
- 분석 lease는 660초예요. 현재 메타데이터 15초·생성 전체 600초 제한에 여유를 더했어요.
  메일 lease는 120초예요. 호출 직전에 같은 실행권을 조건부로 연장해 준비 시간을 호출 예산에서 빼지 않아요.
  만료 시 아직 SMTP가 진행 중일 가능성을 미발송으로 추정하지 않아요. 회수 전에 도착한 결과는 token이
  여전히 일치할 때 저장하고, 이미 회수·종료된 시도를 늦은 응답으로 덮어쓰지 않아요.
- `dispatched_at`은 외부 생성·발송 호출 직전에 저장하는 호출 의도예요. 실제 물리적 HTTP 요청 수가 아니에요.
  이 값이 없는 만료 시도만 같은 시도 번호로 이어받아요. 값이 있으면 분석은 `provider_outcome_unknown`,
  메일은 `ambiguous`로 종료하고 자동 재호출하지 않아요. 표식 저장과 실제 호출 사이 중단도 보수적으로 같은 처리를 해요.
- 분석 성공 시 시도·공통 보고서·작업 완료·대기자의 개인 권한·요청 완료를 한 batch로 저장해요.
  완성 보고서 재사용도 개인 요청과 권한을 한 번에 저장해요. 조회는 어떤 저장이나 재시도도 하지 않아요.
- 생성 설정은 서버가 구성한 정규화 JSON의 SHA-256으로 식별해요. 실행 직전에 현재 지원하는 설정·키를
  다시 대조해요. 모델·Interactions Agentic·원본 프롬프트 버전·600초·SDK 기본 재시도는 ADR-0017을 유지해요.
  프롬프트나 SDK 재시도 의미가 바뀌면 이 생성 설정 버전도 바꿔야 해요.
- 분석 재시도는 사용자 요청과 관찰한 마지막 시도 번호의 조건부 갱신으로만 접수해요. 이전 retry 응답이
  유실돼 다시 와도 다음 실패를 건너뛰어 새 시도를 만들지 않아요. 총 3시도 상한과 종료 이력을 유지해요.
- SDK가 마지막으로 반환한 5xx만으로 내부 재시도의 모든 호출이 미실행이었다고 확인할 수 없어요.
  실행기는 이를 결과 불명으로 보존해요. `SummaryError` 자체의 분류·SDK 설정을 바꾸지는 않아요.
  메타데이터 실패처럼 생성 미호출을 아는 경우는 명시적 재시도가 가능해요.
- 메일은 기존 보고서만 사용해요. 확실한 일시 거부는 총 3시도 안에서 1분·5분 후 재시도하고,
  사용자 retry도 이 대기를 줄이지 않아요. 구독·주소·개인 권한은 SMTP 호출 직전에 다시 확인해요.
  본문은 plain text와 HTML escape한 `<pre>`로 전달해요. 리포트 메일 디자인은 #15에서 다뤄요.
- `BACKGROUND_JOBS_ENABLED=false`가 기본이에요. #5의 공급자 증거와 #7의 실제 운영 한도를 확인하기 전에는
  원격 자동 호출을 켜지 않아요. false인 scheduled 핸들러는 DB와 공급자를 호출하지 않아요.

## 근거와 대안

2026-10-30 공식 문서와 설치한 Wrangler 4.152.0·workers-types 5.20261019.1의 타입을 확인했어요.

[D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)는 순차 SQL을 트랜잭션으로 처리해요.
기존 작업 테이블과 같은 저장소에서 접수와 결과를 관리하면 D1 저장·외부 실행 시작 사이의 전달 복구가 필요 없어요.
대신 lease·조건부 전이·복구 코드를 앱이 책임져요. 구현은 `src/jobs/analysis.ts`·`delivery.ts`의 두 고정 흐름이며
다른 종류의 작업을 등록하는 범용 실행 엔진이나 추가 서비스는 만들지 않아요.

Workflows는 단계 결과와 재개를 제공해 장기·다단계 작업에 유리해요. 다만 외부 응답 유실의 중복 호출은
별도 보호가 필요하고, D1 접수와 Workflow 생성의 원자성도 해결해야 해요. 현재의 두 공급자 경계에서는
기존 D1 상태를 그대로 사용하는 쪽을 선택했어요. 두 완성 구현의 코드량을 실측 비교한 결론은 아니에요.
[Workflows 무료 요금](https://developers.cloudflare.com/workflows/reference/pricing/)에는 일일 3,000단계와
호출당 CPU 10ms 제한이 있어 CPU 문제를 자동으로 해결하는 대안으로 보지 않아요.

[Workers 한도](https://developers.cloudflare.com/workers/platform/limits/)상 Cron의 wall time은 15분이고
무료 CPU 시간은 10ms예요. `waitUntil()`의 응답 후 30초만으로 현재 최대 600초 생성 호출을 유지할 수 없어
HTTP 응답 이후 장기 실행을 맡기지 않아요. 1분 Cron은 하루 1,440회라는 계산이며 실제 사용량이 아니에요.
[D1 무료 한도](https://developers.cloudflare.com/d1/platform/pricing/)는 일일 읽기 500만 행·쓰기 10만 행이에요.
만료 복구는 종류별 최대 2개로 제한해 한 실행의 DB 하위 요청 수를 제한하고 남은 행은 다음 Cron에서 확인해요.
실제 CPU·행 사용량·원격 스케줄 지연·여러 키가 공유하는 Gemini 사용량은 아직 측정하지 않았어요.

## 가정·한계와 영향

- Cron 시작까지 지연이 생기며 처리량은 종류별 한 실행으로 제한돼요. 실제 대기 시간 요구와 측정이 이 범위를
  넘으면 동시성·스케줄·Workflows를 새 기록에서 재검토해요.
- 외부 호출과 D1 commit 사이에는 원자성이 없어요. 공급자 성공 후 DB 저장이 실패하면 결과 불명으로 남을 수 있어요.
  이 경우 원문 결과나 공급자 증거를 확인하는 운영 복구가 필요해요. exactly-once 전송·과금은 보장하지 않아요.
- 0004는 기존 행을 삭제하지 않고 실행권 4개 열과 호출 의도 2개 열을 추가해요. 이전 running/started 시도는
  실제 호출 여부를 모르므로 호출 의도를 시작 시각으로 채워 재호출을 막아요. 종료 이력은 변경하지 않아요.
- 무료 D1·CPU 제한으로 저장에 실패하면 접수 성공으로 응답하지 않아요. 호출 전에 중단한 실행은 복구하고,
  호출 후 상태를 잃으면 재시도 가능 실패로 바꾸지 않아요. 무료 플랜 내 실제 운영 가능성은 미검증이에요.
- 이 함수들은 인증된 서버 호출부를 위한 내부 기능이에요. 세션·접수 한도·HTTP 계약은 #9·#11,
  영상 발견과 발송 대상 생성은 #14·#15에 남아요. 인증 메일 outbox를 구현한 것은 아니에요.

## 검증과 재검토 조건

`test/jobs.test.ts`와 `test/job-migration.test.ts`는 실제 workerd·로컬 D1을 사용해요. 공급자 응답은 fixture예요.
반복 접수·여러 사용자 합류·동시 claim·호출 전 재개·호출 후 만료·오래된 token·저장 실패 rollback·
성공 저장 후 반복 전달·stale retry·3시도 상한·SMTP 설정 변경과 결과 불명을 검사해요.
scheduled 핸들러에서 기존 메타데이터·Gemini SDK 코드로 들어가 응답 fixture를 저장하는 경로도 검사해요.

2026-10-30 macOS arm64, Bun 1.4.4·Node.js 24.22.1·Temurin 25.0.5+8에서 확인했어요.

- 새 작업·migration 검사 40개를 포함해 workerd 160개, API 도구 16개, 공통 도구 49개가 통과했어요.
- `ANDROID_HOME=/Users/ted/Library/Android/sdk mise run check`가 통과했어요. API 타입·번들 dry-run,
  Android 포맷·Lint·단위 테스트·debug 빌드, 두 Terraform root의 backend 없는 init·validate를 포함해요.
- 별도 Wrangler 로컬 DB에 0001~0004를 적용하고 재실행의 `No migrations to apply`를 확인했어요.
  실제 SQLite와 ERD의 17개 테이블·122개 열이 일치하고 외래키 위반은 0개예요.
- `git diff --check`와 새 파일의 공백·문서 상대 링크를 확인했어요. 기준은 `37fea11021e4472c38c7bbe8a0811f26b8406c09`
  위의 미커밋 작업 트리예요. 커밋·push·PR·원격 적용은 하지 않았어요.

원격 Cron·공급자 성공·기기 UI·무료 운영 성립은 로컬 fixture 검사로 대신하지 않아요.
실제 CPU 제한이나 복구 정체가 관찰되면 활성화 전에 실행 방식을 재검토해요.

## 반론과 변경 이력

- 2026-10-30: 공급자 검증 대기로 기능 개발이 지연된다는 요청을 반영했어요. 실행 기반을 먼저 구현하고
  실제 공급자 검증과 활성화 조건은 보존했어요. Workflows 제안은 현재 두 작업의 실행 방식으로 채택하지 않아요.
- 2026-10-30: 실행 플래그와 읽기 어려운 실행기 코드에 대한 사용자 피드백을 반영해 ADR-0023으로 대체했어요.
  최초 검사 결과는 당시 코드 기준으로 보존해요.
