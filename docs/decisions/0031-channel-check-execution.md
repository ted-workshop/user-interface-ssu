# ADR-0031: 채널 확인을 D1 대기열과 첫 기준으로 실행해요

- 상태: 확정
- 작성일: 2026-11-13
- 확정일과 근거: 2026-11-13, 사용자의 #14 구현 시작 요청과 이슈의 완료 기준 범위 안에서 자율 판단했어요.
- 관련 기록: [ADR-0022](0022-d1-scheduled-jobs.md)·[ADR-0023](0023-background-runner-readability.md)의 D1 대기열·1분 Cron,
  [ADR-0018](0018-api-contract-and-policies.md)의 자동화 정책, [ADR-0019](0019-d1-product-schema.md)의 첫 기준·관측 표,
  [ADR-0020](0020-shared-analysis-and-report-permissions.md)의 공통 분석·개인 권한,
  [ADR-0027](0027-no-orm-typed-rows.md)의 행 타입, [ADR-0030](0030-channel-settings-http.md)의 구독·수신 설정을 적용해요.
- 구현·검증 상태: 확인 작업 표·공식 YouTube 조회·예약/지금 확인 HTTP·실행기를 구현하고 로컬 workerd 검사를 통과했어요.
  실제 YouTube 프로젝트 할당량, 원격 Cron, Android 화면은 확인하지 않았어요.

## 문제와 현재 상태

[#14](https://github.com/ted-workshop/user-interface-ssu/issues/14)는 채널을 처음 등록했을 때 과거 영상을 대량 생성하지 않고,
이후 새 영상만 자동 요약 흐름에 연결하는 실행을 요구해요. [기능 명세](../qletter/02-functional-spec.md) F-06의
수용 기준 AC-06은 첫 확인·빈 채널·반복 확인·확인 실패를 구분해요.

기준인 [PR #46](https://github.com/ted-workshop/user-interface-ssu/pull/46)(#13) 브랜치에는 `channels`·`channel_subscriptions`·
`subscription_videos`·`videos` 표와 구독·수신 주소·주기 설정 HTTP가 있어요. 첫 기준·확인 작업·공식 영상 목록 조회·
Cron 연결은 없었어요. 이 기록은 그 브랜치 위에 쌓는 #14 변경에 대한 판단이에요.

## 결정

- 새 표 두 개를 추가해요. `channel_checks`는 사용자별 확인 작업의 `queued|running|completed|failed`,
  수동 여부, 실행권 token, 시작·종료 시각, 확인 자체의 실패 코드를 담아요.
  `channel_check_results`는 확인 한 번에서 시도한 구독별 `completed|failed`, 실패 코드, 그때의 `lastCheckedAt`을 담아요.
  새 의존성·ORM·범용 작업 엔진은 추가하지 않고 기존 `jobs/` 실행기와 행 타입 규칙을 따라요.
- 확인은 [ADR-0022](0022-d1-scheduled-jobs.md)의 1분 Cron에서 전역 하나만 실행해요. 시작 전에 15분 넘게 `running`인
  확인을 `failed`·`interrupted`로 끝내고, 남은 대기 확인은 같은 실행에서 이어가요.
  구독별 공급자 호출은 실행 직전에 활성 상태·확인된 수신 주소·확인 주기를 다시 조회하고, 중지·삭제된 구독은 건너뛰어요.
- 예약 확인은 `nextCheckAt`이 없거나 지난 활성 구독만, `지금 확인`은 본인의 활성 구독을 대상으로 해요.
  계정당 대기 하나·실행 하나를 허용해, 진행 중인 지금 확인은 같은 자원을 `200`으로 반환해요. 아직 시작하지 않은
  예약 확인은 결과가 없으므로 지우고 지금 확인으로 바꿔요. 예약 확인이 실행 중이면 끝난 뒤 실행할 지금 확인을
  대기시키고 `202`로 새 작업을 돌려줘요. 60초 간격은 사용자가 누른 지금 확인 생성에만 적용하고 예약 확인은 포함하지 않아요.
  한 확인의 채널 상한 때문에 지금 확인이 일부만 보고 끝나지 않도록, 남은 활성 구독이 있으면 같은 묶음의
  후속 지금 확인을 자동으로 대기시키고 `nextCheckId`로 알려줘요. 후속 작업은 첫 작업의 `continued_from_id`를
  가리키며, 같은 묶음에서 이미 시도한 구독은 결과가 있어 다시 보지 않아요.
  서버에 `YOUTUBE_API_KEY`·Gemini 생성 설정이 없으면 예약 행을 만들지 않고 HTTP는 `503 AUTOMATION_UNAVAILABLE`이에요.
  활성 구독·확인된 주소가 없으면 `409 AUTOMATION_NOT_READY`예요.
- 공식 YouTube Data API 두 번으로 최근 영상 50개를 읽어요. `channels.list`(`part=contentDetails`)에서 업로드 재생목록 ID를
  찾고 `playlistItems.list`(`part=snippet`, `maxResults=50`)에서 영상 ID·제목·게시 시각을 검증해요.
  입력 URL을 직접 열지 않고 고정 endpoint에 `x-goog-api-key`로 전달하며 10초 기한·redirect 거부·자동 재시도 없음은
  [ADR-0030](0030-channel-settings-http.md)과 같아요.
- 첫 성공 확인은 응답의 영상 ID 전체를 `is_baseline=1`로 저장하고 `baselineInitializedAt`을 기록해요.
  빈 채널도 기준을 기록해 첫 업로드를 반복해서 제외하지 않아요. 첫 확인이 실패하면 기준·`lastCheckedAt`을 만들지 않아요.
  이후 확인은 이 구독에서 관측하지 않은 영상 ID만 `summary_requests.origin='channel'`로 기존 분석 흐름에 접수해요.
  같은 영상·생성 설정은 기존 분석 작업·보고서를 재사용하므로 확인이 반복돼도 결과가 늘지 않아요.
- 영상 관측 기록은 채널 요청 접수보다 먼저 저장해요. 기존 `summary_request_observation` 트리거가 채널 요청에
  관측 기록·활성 구독·기준 초기화를 요구하기 때문이에요. 접수 전에 프로세스가 끝나 요청 없이 관측만 남으면
  다음 확인에서 그 관측을 이어서 접수해요. 접수가 저장 실패로 끝난 이번 시도는 관측을 되돌려 다음 확인에서
  다시 처리해요. 접수 statement는 활성 구독과 확인된 수신 주소를 같은 SQL에서 다시 확인해,
  확인 도중 마지막 주소가 삭제되면 새 요청을 만들지 않아요. 관측과 접수 사이의 중단은 원자적이지 않지만,
  다시 접수해도 기존 분석 작업을 재사용해 중복 보고서가 생기지 않아요.
- 확인이 성공한 구독은 `lastCheckedAt=지금`, `nextCheckAt=지금 + 주기`로 갱신해요. 채널별 공급자 실패와
  영상 기록·접수 중 저장 실패(`processing_failed`)는 다른 채널의 확인을 막지 않고
  `lastCheckedAt`을 유지하고 `nextCheckAt`만 `지금 + 주기`로 미뤄 다음 확인에서 다시 시도해요.
  확인 `completed`는 영상 수집·기준 갱신·새 영상 접수까지 마쳤다는 뜻이고, 개별 영상의 분석 완료와는 다른 상태예요.
- 확인 HTTP는 `POST /v1/channel-checks`(빈 본문 또는 `{}`)와 `GET /v1/channel-checks/{id}`이고,
  세션 사용자로만 조회·생성해요. 다른 사용자의 확인은 같은 `404 NOT_FOUND`예요. 확인 객체는
  `id`, `status`, `failureCode`, `createdAt`, `finishedAt`, `channels[]`(구독 ID·제목·상태·실패 코드·마지막 성공 시각)예요.
  채널별 실패 코드는 `provider_unavailable`·`invalid_response`·`processing_failed`, 확인 자체의 실패 코드는 `configuration`·`interrupted`예요.
- 채널 자동 접수도 직접 요약과 같은 계정별 UTC 하루 3회 접수 한도를 함께 써요. 채널 접수가 한도를 넘은 영상은
  관측만 남기고 다음 확인에서 다시 시도해, 한도 때문에 접수하지 못한 사실이 영구 손실로 이어지지 않게 해요.
- 한 확인은 최근 확인이 오래된 순으로 채널 2개·새 분석 2건까지만 처리해요. 무료 Workers invocation의 subrequest 50개와
  Gemini 사용량을 함께 지키기 위한 실행 예산이고, 남은 구독은 `lastCheckedAt`이 오래된 순서로 다음 확인에서 이어가요.
  남은 영상은 관측하기 전에 멈춰 다음 확인에서 처음 본 영상으로 다시 처리해요. 확인 주기·수집 개수·동시 실행은
  공급자가 보장한 할당량이 아니므로 운영 측정 뒤 재검토해요.

## 근거와 대안

2026-11-13 확인한 [YouTube Data API 할당량 비용 문서](https://developers.google.com/youtube/v3/determine_quota_cost)는
`channels.list`·`playlistItems.list`를 각각 1 unit으로 적고, `search.list`·`videos.insert`를 제외한 endpoint 합계의
기본 일일 한도를 10,000 units로 안내해요. 이 근거로 채널 하나를 확인할 때 두 번 호출하면 계산상 2 units이에요.
이 값은 계산이고 실제 프로젝트의 잔여량·분당 한도는 확인하지 않았어요.

RSS 피드(`youtube.com/feeds/videos.xml`)는 키 없이 최근 15개를 받을 수 있지만, 이 제품이 이미 공식 Data API로 채널 신원을
확인하고 있어 출처·응답 검증을 한 경로로 합치는 편이 오류 원인을 줄여요. 50개까지 확인할 수 있는 `playlistItems.list`를
선택했고 RSS는 채택하지 않았어요. `search.list`로 채널 영상을 검색하면 호출당 100 units라 반복 확인 비용이 커서 쓰지 않아요.

확인 작업을 표로 나눈 이유는 `queued|running|completed|failed` 상태, 시도한 채널별 실패, 마지막 성공 시각을
서로 다른 수명으로 보존하기 위해서예요. 분석·발송 행에 상태를 섞으면 확인 완료와 개별 분석 완료를 구분하기 어려워요.
별도 메시지 큐·Workflows는 [ADR-0022](0022-d1-scheduled-jobs.md)의 판단대로 추가하지 않았어요.

2026-11-13 확인한 [Workers 한도 문서](https://developers.cloudflare.com/workers/platform/limits/)는 무료 플랜의
subrequest를 invocation당 50개로 제한하고, D1·KV·R2 같은 Cloudflare 서비스 호출도 subrequest로 센다고 안내해요.
Cron invocation의 wall time은 15분, 무료 CPU 시간은 10ms예요. 채널 확인은 구독마다 공식 조회 2회와 D1 읽기·쓰기가
붙고 같은 invocation에서 분석·발송·인증 메일이 함께 실행될 수 있어, 채널·새 분석 수를 제한하지 않으면 50개를 넘을 수 있어요.
이 계산은 호출 횟수 기준 추정이며 실제 invocation의 subrequest 수는 배포 환경에서 측정하지 않았어요.

[`docs/gemini.md`](../gemini.md)의 2026-10-30 AI Studio 관찰에는 이 키의 RPM 5·RPD 20이 적혀 있고, 사용자가 무료 플랜을
확인했어요. 실제 잔여량·모델별 한도는 미확인이지만, 채널 자동 접수를 무제한으로 두면 작은 버스트로도 프로젝트 일일
할당량을 소진해 직접 요약까지 실패할 수 있어 직접 요약과 같은 하루 3회 접수 한도를 공유해요. 자동화만의 별도 한도
버킷은 테이블·정책을 더 만들고 사용자에게 두 한도를 설명해야 해서, 현재 규모에서는 기존 접수 차감을 재사용하는 쪽을 택했어요.

채널 확인 HTTP의 `지금 확인`이 예약 확인을 재사용하면 기한 된 구독만 확인하고 끝나 사용자가 기대한 전체 확인과 달라요.
그래서 확인 작업에 계정당 `queued` 하나·`running` 하나를 허용하는 partial unique index 두 개로 바꿨어요.
예약 확인이 실행 중이어도 지금 확인을 대기시킬 수 있고, 전역 실행 하나 제한은 그대로 유지해 동시 공급자 호출을 막아요.

한 번에 확인 하나만 실행하는 이유는 공급자 quota 보호와 중첩 Cron의 동시 호출 방지예요. 대신 채널이 많은 계정은
한 확인에서 모든 구독을 처리하고, 다른 계정은 다음 1분 실행을 기다려요. 이 지연이 제품 요구를 넘으면 동시성·
실행 시간을 별도 기록에서 재검토해요.

관측 기록을 먼저 저장하는 순서는 기존 스키마 트리거가 강제하는 제약이에요. 순서를 바꾸려면 채널 요청 접수 트리거를
완화해야 하는데, 그러면 관측 없이 채널 요청이 생길 수 있어 채택하지 않았어요. 대신 관측 선저장·재접수와 실패 시
보상 삭제로 "본 영상을 영영 건너뛰는" 상태를 피해요.

## 가정·한계와 영향

- 마이그레이션 `0009_channel_checks.sql`은 기존 행을 바꾸지 않고 표·인덱스·트리거만 추가해요. 0008(리포트 댓글) 뒤에
  적용되고 두 파일은 서로 의존하지 않아요. 2026-11-13 `main`의 0008과 함께 로컬 D1에 적용해 검사를 확인했어요.
  원격 D1에는 아직 적용하지 않았어요.
  0009를 제자리에서 고쳤으므로 이미 로컬에 적용한 DB는 CHECK가 바뀌지 않아 로컬 D1 상태(`apps/api/.wrangler/state`)를 지우고 `mise run api:db:migrate`로 다시 만들어야 해요.
- 확인 한 번은 채널 2개까지 공급자 호출 2회씩과 D1 읽기·쓰기를 사용하고, 새 분석은 2건까지만 접수해요.
  1분 Cron·전역 하나 실행이라 처리량은 `분당 2채널·2영상`이고, 사용자·채널이 늘면 확인 대기가 길어져요.
  실제 subrequest 수·quota·Cron 지연은 측정하지 않았어요.
- 채널 확인은 직접 요약과 같은 하루 3회 접수 한도를 나눠 써요. 사용자가 직접 요약을 많이 하면 그날 자동 요약이
  다음 확인으로 밀리고, 반대로 자동 접수가 먼저 한도를 쓰면 직접 요약이 `429 USAGE_LIMIT_REACHED`를 받을 수 있어요.
  자동화 실패는 확인 결과가 아니라 개별 요청 상태로 보이고, 남은 영상은 다음 확인에서 다시 시도해요.
- 최근 50개 목록만 보므로 확인 사이에 50개를 넘는 업로드가 있으면 목록 밖으로 밀린 오래된 영상은 자동 처리되지
  않을 수 있어요. 페이지 토큰으로 과거 목록을 더 읽지 않으며, 원하는 영상은 직접 URL로 요청해야 해요.
  장기간 중지한 동안의 모든 영상을 복구하거나 제공 정보보다 빠르게 감지한다고 보장하지 않아요.
- 확인 작업·결과 행은 삭제·정리 정책 없이 누적돼요. `nextCheckId`가 있는 동안 앱이 후속 작업을 조회하지 않으면
  사용자는 첫 작업의 `channels`만 볼 수 있어요. 묶음의 결과를 한 화면에 모으는 API는 만들지 않았어요. D1 저장·읽기 사용량이 문제가 되면 보존 기간·집계 방식을 새 기록에서 정해요.
- 접수 실패 뒤 관측을 지우는 보상 삭제만 실패하고 채널 실패 기록은 성공하면 그 영상은 요청 없이 관측만 남아요.
  이 상태는 다음 확인에서 이어서 접수해요. 보상 삭제가 성공한 영상이 그사이 공급자 목록 밖으로 밀리면 자동 처리되지 않아요.
- 채널별 저장 실패를 `processing_failed`로 남기는 복구 쓰기까지 실패하면(DB 전체 장애) 확인은 `running`으로 남고
  15분 뒤 `interrupted`로 끝나요. 이때 로그에는 예외 이름과 작업 ID만 남기고 메시지 원문은 남기지 않아요.
- 서버 설정이 빠진 채 이미 대기 중이던 확인은 한 번 `failed`·`configuration`으로 끝나고, 이후 예약 행을 만들지 않아요.
  설정을 복구하면 다음 예약 실행에서 다시 시작해요.
- 이번 변경은 채널 리포트 발송(#15)과 홈 현황(#16)을 구현하지 않아요. 새 영상은 분석 작업·보고서만 만들고 발송 행을 만들지 않아요.
- Android 화면·원격 배포는 이 범위가 아니에요. 실제 YouTube 호출과 원격 Cron은 미검증이에요.

## 반론과 변경 이력

- 2026-11-13: #14를 PR #46(#13) 브랜치 위에 쌓아 구현했어요. 선행 PR이 리베이스되면 이 변경도 같은 기준으로 다시 검증해요.
- 2026-11-13: 구현 중 기존 `summary_request_observation` 트리거가 채널 요청 접수 전에 관측 기록을 요구하는 것을 확인했어요.
  관측을 먼저 저장하고 접수 실패 시 지우는 방식으로 바꿨고, 검사로 요청 없이 관측만 남지 않는 흐름을 확인해요.
- 2026-11-13: 리뷰에서 영상 기록·접수 중 DB 예외가 채널 단위로 격리되지 않는 문제를 확인했어요. 예외가 나면 확인이
  `running`으로 남아 전역 하나 실행 제한 때문에 모든 계정이 15분 막히고, 실패한 구독의 `nextCheckAt`이 그대로라
  다음 예약에서 같은 구독이 다시 먼저 뽑힐 수 있었어요. 채널별 결과 코드 `processing_failed`를 추가해
  해당 구독만 다음 주기로 미루고 다음 채널로 넘어가게 바꿨어요. 보상 삭제 경로는 `summary_requests` 삽입 실패 트리거로, 첫 기준 저장 실패는 `subscription_videos` 삽입 실패 트리거로 확인해요.
- 2026-11-13: 리뷰에서 프로세스가 관측과 접수 사이에서 끝나면 그 영상을 영구히 건너뛰는 문제와, 확인 도중 마지막
  수신 주소가 삭제돼도 새 분석을 접수하는 문제를 확인했어요. 요청이 없는 관측을 다음 확인에서 이어서 접수하고,
  관측·기준·다음 시각 갱신·접수 SQL에 활성 구독과 확인된 수신 주소 조건을 넣었어요. 관측만 남은 상태, 공급자 응답
  중 주소 삭제, 첫 확인 중 주소 삭제를 회귀 검사로 추가했어요. 최근 50개만 읽고 페이지 토큰을 쓰지 않는 실제 범위에
  맞춰 문서의 "다음 확인에서 처리" 보장 문구를 고쳤어요.
- 2026-11-13: 리뷰에서 채널 자동 접수가 일일 접수 한도를 우회하는 점, 구독이 많으면 한 Cron invocation의 subrequest 한도에
  걸려 뒤쪽 채널이 계속 실패할 수 있는 점, 예약 확인이 대기 중일 때 지금 확인이 기한 된 구독만 보는 점을 확인했어요.
  채널 자동 접수도 직접 요약과 같은 하루 3회 접수 한도를 쓰고, 한 확인은 채널 2개·새 분석 2건으로 제한하며
  오래 확인하지 않은 구독부터 처리해 남은 구독이 다음 확인에서 이어지게 했어요. 지금 확인은 대기 중인 예약 확인을
  바꾸고, 예약 확인이 실행 중이면 끝난 뒤 실행할 지금 확인을 대기시켜요. 계정당 queued·running partial unique index를
  분리하고, 예약 확인 전환·대기, 채널 상한, 한도 공유 회귀 검사를 추가했어요.
- 2026-11-13: 승인 리뷰에서 지금 확인이 채널 2개 상한 때문에 일부 채널만 확인하고 끝나는 점을 확인했어요.
  남은 활성 구독이 있으면 같은 묶음의 후속 지금 확인을 자동으로 대기시키고 `nextCheckId`로 알려주도록 했어요.
  후속 작업은 `continued_from_id`로 첫 작업을 가리키고, 같은 묶음에서 결과가 있는 구독은 다시 조회하지 않아
  무한 후속 작업 없이 전체 채널을 확인해요. 3개 채널의 지금 확인이 2개+1개 작업으로 끝나는 회귀 검사를 추가했어요.
- 2026-11-13: 채널 리포트 발송(#15)은 [ADR-0037](0037-channel-report-delivery.md)에서 이어서 구현했어요.
  확인·분석 경계는 그대로이고, 리포트 완료 저장 batch가 발송 행을 만드는 결정만 추가됐어요.
