# ADR-0002: 백그라운드 처리에 Workflows 사용을 제안해요

- 상태: 기각
- 작성일: 2026-10-20
- 기각일·근거: 2026-10-30, [ADR-0022](0022-d1-scheduled-jobs.md)에서 D1 대기열과 예약 실행을 선택했어요. 아래는 당시 제안과 근거를 보존한 기록이에요.
- 확정일과 근거: Workflows 제품의 채택은 미확정이에요. 실행 방식을 나누는 구조는
  [ADR-0003](0003-shared-modules-sync-async.md)에서 사용자 승인으로 확정했어요.
- 관련 기록: [ADR-0001](0001-workers-d1-free-tier.md), [ADR-0003](0003-shared-modules-sync-async.md)
- 구현·검증 상태: 공식 문서와 제품 계약을 비교했어요. 실행 코드·로컬 검사·배포·실제 공급자 검증은 없어요.

## 문제와 현재 상태

[기능 명세](../qletter/02-functional-spec.md)의 F-02는 앱을 닫아도 요청이 유지되고,
다시 열었을 때 상태를 조회할 수 있어야 한다고 정해요.
F-07은 메일 실패 시 리포트를 유지하고 발송만 재시도하도록 정해요.
따라서 요약 요청의 HTTP 응답과 오래 걸리는 처리를 분리하고 단계별 실패를 복구할 방법이 필요해요.

서버의 현재 구현은 health·공통 오류 응답까지예요. 실행 방식의 경계는 ADR-0003을 따르고,
아래의 Workflows 사용과 구체적인 API 계약은 제안이에요.

## 이벤트 기반 처리를 추천하는 범위와 이유

추천하는 범위는 하나의 API 코드베이스 안에서 요약·메일을 영속적인 비동기 작업으로 처리하는 것이에요.
로그인·권한 확인·조회·설정 저장은 HTTP 요청에서 처리하고, 요약 요청이나 새 영상 발견을 계기로
백그라운드 처리를 시작해요. 리포트 저장과 메일 발송의 순서·재시도는 명시적인 Workflow로 관리하는 제안이에요.

- F-02의 앱 재진입 요구 때문에 처리 수명을 앱의 HTTP 연결과 분리해야 해요.
  접수한 작업과 상태를 영구 저장하면 앱은 같은 요청 ID로 결과를 다시 조회할 수 있어요.
- F-07의 발송 실패 복구 요구 때문에 요약·저장·발송의 완료 상태를 분리해야 해요.
  예를 들어 요약과 저장은 끝났지만 메일만 실패했다면 저장된 리포트를 사용해 발송만 재시도해야 해요.
- F-01과 F-06의 직접 요청·예약 확인은 같은 요약 처리를 시작하는 두 경로예요.
  공통 작업 흐름을 이용하면 중복 처리·실패 복구 규칙을 함께 적용할 수 있어요.
  이 재사용은 공유 함수로도 가능하므로 이벤트 기반 구조만의 이점으로 보지는 않아요.

이 요구들은 영속적인 비동기 처리와 복구 상태를 설계할 근거예요.
특정 이벤트 버스나 Workflows 제품이 유일한 해답이라는 증거는 아니에요.
[이벤트 기반 아키텍처](https://aws.amazon.com/event-driven-architecture/)는 발생한 상태 변화를
생산자·라우터·소비자가 전달하고 처리하는 구조를 설명해요.
지금 제안은 작업을 시작하는 계기와 실행 순서를 명확히 하는 범위이며,
모든 상태 변경을 이벤트로 전파하거나 여러 서비스를 이벤트 구독으로 연결하는 구조까지 포함하지 않아요.

핵심 기대 효과는 실패가 난 단계만 복구하는 것이에요. 성능 향상·비용 절감은 아직 측정하지 않았어요.
이벤트를 발행했다는 사실만으로 작업 지속·중복 방지·단계별 복구가 보장되지는 않아요.

### 모든 기능을 이벤트 기반으로 통일하자는 반론

사용자는 같은 구조로 통일하면 구현을 굳이 나눌 필요가 없지 않은지 물었어요.
이벤트 기반 구조와 비동기 큐를 같은 뜻으로 취급하면 이 반론을 제대로 비교할 수 없어요.
[Microsoft의 도메인 이벤트 설명](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/domain-events-design-implementation)은
도메인 이벤트를 같은 프로세스 안에서 동기 또는 비동기로 처리할 수 있다고 구분해요.
따라서 이벤트를 활용하는 모듈 구조가 모든 요청의 큐 처리를 요구하지는 않아요.

코드 구조·입력 검증·에러·작업 ID·로그 규칙을 통일하면 기능마다 새 규칙을 배울 부담을 줄일 수 있어요.
같은 기능의 로직을 HTTP 처리와 백그라운드 처리에서 중복 작성할 필요도 없어요.
한 코드베이스의 기능 모듈을 호출하고, 실행 수명과 복구 요구에 맞춰 호출 경로를 정하는 제안이에요.
통일된 형식만을 위해 공통 이벤트 버스나 모든 기능의 구독 핸들러를 추가하는 것은 아직 제안하지 않아요.

예를 들어 F-11의 로그인은 비밀번호 검증과 세션 생성 결과가 있어야 성공을 응답할 수 있어요.
이를 비동기 큐로 처리해도 API가 결과를 기다리거나 앱이 별도로 완료를 확인해야 해요.
결과 연결·대기 시간 제한·중복 처리·큐 장애라는 관리 항목이 추가되고,
큐를 필수 경로로 만들면 큐 장애가 로그인 실패의 원인이 될 수 있어요.
이는 가능한 설계의 영향 분석이며 현재 시스템에서 관찰한 장애나 지연 측정은 아니에요.
[Microsoft의 아키텍처 지침](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/event-driven)은
단순한 요청·응답에는 비동기 오류 처리·일관성 관리의 부담을 따져야 하며,
메시지 기반 요청·응답에도 결과를 연결하고 기다리는 처리가 필요하다고 설명해요.

즉시 결과가 필요한 로그인·조회와, 접수 후 앱 연결 없이 이어가야 하는 요약·발송은
서로 다른 실행 요구를 가지므로 이 경계에서 실행 방식을 나누는 쪽을 추천해요.
여러 독립 모듈이 같은 사실에 반응해야 하는 요구가 확인되면 도메인 이벤트 사용 범위를 다시 검토해요.
이때도 즉시 완료해야 할 작업과 나중에 처리해도 되는 후속 작업의 경계는 명시해요.
위 공식 자료의 확인 날짜는 2026-10-20이며 도구·비용·성능의 실측 검증은 아직 없어요.

## 제안

- Workers의 Hono API에서 인증·입력·중복 요청을 확인하고, 접수한 요청 ID와 `202`를 반환해요.
  같은 계정의 기존 요청·결과를 반환하는 응답 계약은 별도 API 설계에서 정해요.
- Workflows에서 Gemini 요약, 리포트 저장, 채널 자동 요약의 메일 전달을 단계로 나눠 처리해요.
  직접 요약은 메일을 보내지 않는 기존 제품 규칙을 유지해요.
- 사용자에게 필요한 요청 상태와 리포트는 D1에 저장해요.
  영구 보관할 데이터를 Workflow 실행 이력에만 의존하지 않아요.
- 채널 확인은 예약 실행에서 시작하고 직접 요청과 같은 요약 처리를 이용해요.
  확인 주기·예약 방식·동시성·재시도 정책은 아직 정하지 않았어요.

## 근거와 대안

[Workflows 개요](https://developers.cloudflare.com/workflows/)는 다단계 실행의 상태 보존과 실패 재시도를 제공해요.
영상 처리 후 리포트를 저장하고, 메일이 실패하면 해당 단계부터 복구하려는 요구에 맞는다고 판단해요.
성공한 단계의 결과를 보존하는 기능을 이용하면 처리 단계 관리 코드를 줄일 수 있을 것으로 예상해요.
코드량·비용 감소를 실제로 측정한 결과는 아니에요.

[Queues](https://developers.cloudflare.com/queues/reference/delivery-guarantees/)도 유효한 대안이에요.
독립적인 작업을 메시지로 전달하고 워커에서 처리하기 좋아요.
Qletter의 다단계 진행·실패 복구 상태는 별도로 관리해야 하므로 먼저 Workflows를 검토해요.
Queues는 적어도 한 번 전달을 보장해 중복 전달이 가능하고,
Workflows의 [단계 재시도](https://developers.cloudflare.com/workflows/build/rules-of-workflows/) 역시
외부 API의 중복 부작용을 자동으로 막아주지는 않아요.

D1 작업 테이블과 예약 실행만으로 처리하는 방식도 비교할 수 있어요.
사용하는 제품 수를 줄일 수 있지만 작업 점유, 오래 멈춘 작업의 회수, 재시도와 단계별 상태 관리를
앱에서 구현해야 해요. 작은 흐름에서는 이 방식이 더 단순할 수도 있어요.
Workflows가 이런 관리 코드를 얼마나 줄이는지와 무료 사용량을 함께 비교해야 해요.

HTTP 요청 하나에서 끝까지 기다리는 방식은 코드가 단순해요.
다만 앱 연결이 끝난 뒤의 지속 처리와 재진입·단계별 복구는 별도로 보장해야 해요.
[Workers 실행 한도](https://developers.cloudflare.com/workers/platform/limits/)에 따르면
응답·연결 종료 후 `waitUntil()`이 연장하는 시간에도 제한이 있어 이 기능만으로 긴 처리를 맡기기 어려워요.

공식 출처의 확인 날짜는 2026-10-20이에요.

## 가정·한계와 영향

- [무료 요금](https://developers.cloudflare.com/workflows/reference/pricing/)은 하루 3,000단계이고,
  실행 요청 한도는 Workers와 공유해요. [단계별 CPU 한도](https://developers.cloudflare.com/workflows/reference/limits/)도
  있어 실제 Gemini SDK 호출·결과 처리와 예상 사용량을 확인해야 해요.
- D1에 요청을 저장하는 것과 Workflow를 시작하는 것은 하나의 원자적인 저장 작업이 아니에요.
  사이에 실패했을 때 실행을 빠뜨리지 않고 복구할 방법이 필요해요. 아직 구현·검증하지 않았어요.
- 외부 API 응답이 유실된 경우 재시도가 요약 비용이나 메일을 중복 발생시킬 수 있어요.
  제공자의 중복 방지 지원과 결과 확인 방법을 검토해야 해요.
- 채널 중지·삭제나 수신 설정 변경을 대기 중인 작업과 발송 재시도에 반영해야 해요.
  이전에 읽은 설정을 Workflow 결과로 보존하는 것만으로는 중단 조건을 지키기 어려워요.

## 검증과 재검토 조건

아래 항목을 설계하고 검증한 뒤 채택 여부를 정해요. 현재 모두 미검증이에요.

- 공개 영상 하나가 실제 Gemini 호출·리포트 저장·계정별 조회로 이어져요.
- 요청 저장 직후 실행 시작에 실패해도 요청이 유실되지 않고 복구돼요.
- 같은 요청의 반복 접수·단계 재시도에서 리포트가 중복 생성되지 않아요.
- 메일 실패와 재시도가 새 요약을 만들지 않고, 이미 성공한 수신 주소에 재발송하지 않아요.
  응답 유실처럼 발송 결과를 모르는 경우도 다뤄요.
- 채널 중지·삭제·수신 설정 변경 후 중단 조건을 재확인해요.
- 앱 재진입·실행 중단·무료 한도 오류를 복구하고, 예상 사용량이 무료 범위에 들어가요.

단순한 Queues 소비자만으로 같은 복구 요구를 더 적은 코드와 운영 부담으로 충족하거나,
Workflows 한도·SDK 호환성·실측 비용이 맞지 않으면 제안을 수정하거나 기각해요.

## 반론과 변경 이력

- 2026-10-20: Workers·D1 확정과 Workflows 채택을 구분해 제안으로 기록했어요.
  무료 운영 가능성과 외부 호출의 중복 방지·실행 누락 복구는 검증 전이에요.
- 2026-10-20: 사용자가 이벤트 기반 처리가 좋은 판단인지와 그 이유를 물었어요.
  영속적인 비동기 처리의 근거를 F-02·F-07에 연결하고, 서버 전체의 이벤트 기반 구조와 적용 범위를 구분했어요.
  D1 작업 테이블과 예약 실행도 대안에 추가했어요. Workflows의 채택 상태는 제안으로 유지해요.
- 2026-10-20: 모든 기능의 이벤트 기반 통일이라는 반론을 추가했어요.
  앞선 설명에서 가까이 묶었던 이벤트 기반 구조와 비동기 큐를 구분하고,
  통일된 코드 규칙의 이점과 로그인까지 큐를 거치는 추가 비용·실패 경로를 비교했어요.
  한 코드베이스 안에서 실행 요구에 따라 경로를 정하는 제안이며 별도 서버나 로직 중복을 요구하지 않아요.
- 2026-10-20: 사용자가 이 구조 제안이 타당하다고 승인했어요.
  공통 모듈과 동기·비동기 실행 경계는 ADR-0003에 확정으로 분리했어요.
  이 기록의 Workflows 제품 선택과 실제 동작·비용 검증은 제안·미검증 상태를 유지해요.
