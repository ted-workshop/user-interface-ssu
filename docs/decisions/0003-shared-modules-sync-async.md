# ADR-0003: 모듈 규칙을 통일하고 실행 방식은 요구에 맞춰요

- 상태: 확정
- 작성·확정일: 2026-10-20
- 확정 근거: 모든 기능을 이벤트 기반으로 통일하는 대안과 비교한 뒤,
  사용자가 한 Worker 안에서 공통 규칙을 쓰고 실행 요구에 따라 경로를 나누는 제안이 타당하다고 승인했어요.
- 관련 기록: [ADR-0001](0001-workers-d1-free-tier.md), [ADR-0002](0002-workflows-for-background-jobs.md)
- 구현·검증 상태: 구조 선택과 근거를 문서화했어요. 2026-10-24의 런타임·로컬 D1 기반은
  [ADR-0008](0008-workers-d1-local-and-terraform.md)에 있어요. 인증·제품 DB·백그라운드 처리 구현과
  배포·실제 공급자·사용자 흐름 검증은 아직 하지 않았어요.

## 문제와 현재 상태

사용자는 모든 기능을 이벤트 기반으로 만들면 코드의 통일성을 얻을 수 있지 않은지 물었어요.
통일된 구현 규칙의 이점과 기능별 실행·복구 요구를 함께 충족할 구조를 정해야 해요.

[기능 명세](../qletter/02-functional-spec.md)의 F-11은 로그인 성공·실패와 계정별 접근 제어를,
F-02는 앱 연결과 별개로 유지되는 요약 요청과 상태 복원을 요구해요.
F-07은 리포트가 저장된 뒤 발송만 재시도할 수 있어야 한다고 정해요.
현재 API는 health·공통 오류 응답까지이며, 상세한 현재 상태는 ADR-0001에 남겼어요.

## 결정

- 한 Worker 프로젝트에서 기능 모듈과 입력 검증·에러·요청 및 작업 ID·로그 규칙을 통일해요.
  HTTP 처리와 백그라운드 처리에서 같은 기능의 비즈니스 로직을 중복 작성하지 않아요.
- 로그인·권한 확인·조회·설정 저장은 HTTP 요청에서 결과를 확인해 응답해요.
  성공 응답 전에 필요한 검증과 저장을 완료해요.
- 요약·메일은 작업과 진행 상태를 영구 저장하고 HTTP 연결과 별개로 실행해요.
  요약·리포트 저장·발송의 완료 상태를 구분해 실패한 작업을 복구해요.
- 모든 로그인·조회를 큐에 전달하거나 통일된 형식만을 위해 공통 이벤트 버스를 추가하지 않아요.
- 이 결정은 실행 방식의 경계를 정해요. Workflows 등 구체적인 실행 수단은 ADR-0002의 검토 대상이에요.
  상세 API·스키마·재시도 정책은 이어지는 설계에서 근거와 함께 정해요.

## 근거와 대안

같은 모듈 구조와 검증·에러·로그 규칙을 따르면 기능마다 다른 규칙을 익히는 부담을 줄일 수 있다고 판단해요.
이 통일성은 모든 실행을 큐로 보내지 않아도 얻을 수 있어요.
[Microsoft의 도메인 이벤트 설명](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/domain-events-design-implementation)은
같은 프로세스의 이벤트를 동기 또는 비동기로 처리할 수 있다고 구분해요.
이벤트 활용과 비동기 큐를 동일한 선택으로 보지 않아요.

모든 요청을 비동기 큐에 보내면 전달·소비 방식의 형식은 맞출 수 있어요.
하지만 로그인은 결국 비밀번호 검증과 세션 생성 결과를 기다려야 해요.
큐를 거치면 결과 연결·시간 초과·중복 처리와 큐 장애라는 관리 항목이 추가돼요.
현재 로그인 요구에는 이 의존성을 추가할 이점이 충분하지 않다고 판단해요.
[Microsoft의 아키텍처 지침](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/event-driven)은
단순 요청·응답에서 이런 운영 부담을 비교하고, 메시지 기반 요청·응답에도 결과 대기가 필요하다고 설명해요.

반대로 모든 작업을 HTTP 요청 안에서 끝내는 방식은 호출 경로가 단순해요.
다만 요약·메일에는 앱 연결 종료 후의 작업 지속과 단계별 실패 복구를 별도로 보장해야 해요.
따라서 한 코드베이스를 유지하면서 실행 수명과 복구 요구에 맞춰 경로를 나누기로 했어요.
공식 출처 확인 날짜는 2026-10-20이에요. 지연·코드량·비용을 실측 비교한 결과는 아니에요.

## 가정·한계와 영향

공통 규칙의 구체적인 구현과 실제 중복 감소는 아직 확인하지 않았어요.
비동기 작업에는 실행 누락·외부 호출 결과 유실·중복 처리·단계별 상태 복구가 여전히 필요해요.
무료 플랜 안에서 가능한지는 선택한 실행 수단과 실제 사용량으로 검증해야 해요.
구현 전이므로 기존 사용자 데이터의 이전이나 API 소비자 변경은 아직 없어요.

## 검증과 재검토 조건

로그인·계정별 접근 제어, 앱 재진입 시 요청 복원, 중복 요청, 메일만 실패한 뒤의 복구를 검증해요.
실행 누락·응답 유실을 포함한 검사와 실제 공급자·무료 한도 검증은 ADR-0002의 항목을 함께 따라요.
현재 이 동작들은 모두 미검증이에요.

같은 사실을 여러 독립 모듈이 처리할 요구가 생기거나, 측정에서 다른 실행 구조가 같은 보장을
더 적은 코드·비용으로 제공하면 다시 비교해요. 결정 변경은 새 기록으로 남겨요.

## 반론과 변경 이력

- 2026-10-20: 모든 기능을 이벤트 기반으로 통일하자는 반론에 대해,
  이벤트와 비동기 큐의 차이 및 로그인·요약의 실행 요구를 비교했어요.
- 2026-10-20: 사용자의 승인으로 구조를 확정했어요. Workflows 제품 선택이나 구현 완료로 확대하지 않아요.
